# MapReduce Triangle Enumeration With Guarantees

## 논문 정보

| 항목 | 내용 |
| --- | --- |
| 원제 | MapReduce Triangle Enumeration With Guarantees |
| 저자 | Ha-Myung Park, Francesco Silvestri, U Kang, Rasmus Pagh |
| 발표 | CIKM 2014 |
| 제안 알고리즘 | Colored Triangle Type Partition (CTTP) |

## 한 줄 요약

> CTTP는 그래프의 모든 삼각형을 찾는 색상별 작업을 여러 MapReduce 라운드에 나누어 한 라운드의 중간 데이터 피크를 낮추면서, 기본형의 **기대 리듀서 부하**와 추가 조건을 둔 변형의 **고확률 부하**를 각각 분석한다.

## 핵심 내용

- **문제:** 한 라운드에 간선을 여러 리듀서로 복제하는 기존 방법은 그래프보다 훨씬 큰 shuffle 데이터를 한꺼번에 만들 수 있다. 삼각형의 수 자체도 많으므로, 열거 결과와 중간 데이터의 저장 요구를 구분해야 한다.
- **방법:** 4-wise independent 해시로 정점을 색칠하고 TTP의 두 작업군을 유지하되, 색상 번호의 합을 모듈러 연산해 작업별 실행 라운드를 배정한다. 각 라운드는 입력 간선을 다시 읽고 그 라운드에 필요한 사본만 전달한다.
- **보장:** 기본 CTTP는 임의의 입력 그래프에서 $$O(E^{3/2}/(M\sqrt{m}))$$라운드와 기대 총 작업량 $$O(E^{3/2})$$를 제시한다. 리듀서마다 항상 $$m$$ 이하라는 뜻은 아니다. 별도 색칠 방식과 $$m=\Omega(E^{3/4}\sqrt{\log E})$$ 조건을 적용한 정리 3에서야 고확률의 $$O(m)$$ 부하가 나온다.
- **관측:** 논문의 2014년 Hadoop 실험에서 YahooWeb의 최대 64억 간선 부분 그래프는 CTTP만 끝까지 처리했다. 이 결과는 해당 구현과 클러스터의 공간 병목을 보여 주며 모든 시스템의 처리 한계를 정하지 않는다.

## 문제 배경과 계산 모델

입력은 자기 루프와 평행 간선이 없는 단순 무방향 그래프 $$G=(V,E)$$이며, 이하 $$E$$는 문맥에 따라 간선 집합 또는 간선 수를 뜻한다. 목표는 세 간선이 모두 존재하는 모든 정점 삼중항을 열거하는 것이다. 원문 3.2절은 각 삼각형에 대해 로컬 함수 `enum(·)`을 호출하면 된다고 정의한다. 따라서 논문의 열거 시간은 모든 삼각형을 하나의 파일에 기록·보존하는 데 드는 저장 공간까지 보장한 수치가 아니다. 간선 수가 $$E$$여도 삼각형 수는 최악의 경우 $$\Theta(E^{3/2})$$에 이를 수 있다.

$$MR(m,M)$$ 모델에서 $$m$$은 한 map/reduce 함수, 특히 한 리듀서가 사용할 수 있는 메모리 워드 수의 상한이고, $$M$$은 **한 라운드 전체**에 사용할 수 있는 합산 공간이다. 키 $$k$$에 모인 입력의 공간을 $$m_{k,r}$$라 쓰면 각 라운드 $$r$$에서 요구하는 조건은 다음과 같다.

$$
m_{k,r}\le m,\qquad \sum_{k\in K_r}m_{k,r}\le M.
$$

첫 부등식은 과적된 리듀서 하나의 실패를, 둘째는 리듀서가 각각 작아도 전체 shuffle·중간 데이터가 수용량을 넘는 상황을 구별한다. 이론의 메모리 워드와 실험의 머신 RAM 4GB를 동일한 값으로 바로 대입해서는 안 된다.

기존 GP와 TTP는 정점을 분할하고 색상 조합별 작업을 한 라운드에서 수행한다. 간선은 자신이 필요한 여러 작업으로 복제된다. 원문 5.2절의 고른 색 분포 계산에서 GP의 세 색상 작업은 평균 $$9E/\rho^2$$개의 간선을 받지만, TTP의 세 색상 작업은 내부 간선을 빼 평균 $$6E/\rho^2$$개를 받는다. 이는 작업당 입력량의 상수 차이이지 모든 그래프에서 실행 시간이 1.5배 달라진다는 보장은 아니다. CTTP의 새 선택은 TTP식 작업을 없애는 것이 아니라 그 작업을 시간축으로 분산하는 것이다.

## 제안 방법: 색상별 작업을 라운드로 분산하기

기본형은 정점을 $$\rho=\lceil\sqrt{6E/m}\rceil$$개 색 중 하나로 배정한다. 색칠 함수 $$\xi:V\to[\rho]$$는 4-wise independent 함수족에서 무작위로 선택한다. $$E_{i,j}$$는 양 끝점의 색을 정렬했을 때 $$i,j$$인 간선 집합이다. 색은 정점의 고유 ID가 아니라 이번 분할에 붙인 레이블이므로, 한 색의 서로 다른 정점끼리도 실제 간선이 있을 수 있다.

| 삼각형의 색 | 맡는 부분 문제 | 리듀서가 받는 간선 집합 |
| --- | --- | --- |
| 모두 다른 세 색 $$i<j<k$$ (type-3) | 세 색 작업 $$(i,j,k)$$ | $$E_{i,j},E_{i,k},E_{j,k}$$ |
| 정확히 두 정점의 색이 같거나 세 정점 모두 같은 색 (type-2·type-1) | 두 색 작업 $$(i,j)$$, $$i<j$$ | $$E_{i,i},E_{i,j},E_{j,j}$$ |

세 색 작업은 $$\binom{\rho}{3}$$개, 두 색 작업은 $$\binom{\rho}{2}$$개다. 논문이 배치할 전체 부분 문제 수는

$$
K=\binom{\rho}{3}+\binom{\rho}{2}=\frac{\rho(\rho^2-1)}{6}.
$$

라운드 수를 $$R$$이라 할 때 세 색 작업은 $$i+j+k\equiv r\pmod R$$, 두 색 작업은 $$i+j\equiv r\pmod R$$인 라운드 $$r$$에서 처리한다. 매퍼는 간선의 두 끝점 색을 계산한 뒤 **현재** 라운드의 해당 작업 키에만 간선을 보낸다. 리듀서는 자신이 받은 간선으로 로컬 삼각형 열거기를 실행한다. 논문 보조정리 1은 라운드당 작업 수가 대략 $$K/R$$로 분산됨을 보여 준다. $$R$$이 2나 3의 배수이면 정확히 같지는 않지만 편차를 제한한다.

예를 들어 설명용으로 $$\rho=4,R=2$$를 택하면 $$E_{0,1}$$의 한 간선은 두 색 작업 $$(0,1)$$과 세 색 작업 $$(0,1,2)$$, $$(0,1,3)$$에 필요하다. 색 번호 합을 2로 나누면 앞의 둘은 라운드 1, 마지막은 라운드 0으로 배정된다. 한 번에 사본 세 개를 보내는 대신 라운드별 2개와 1개로 나눈 것이다. **전체 전달 횟수가 사라진 것은 아니며**, 다음 라운드에서 원본 입력을 다시 map한다. 이 숫자 예시는 라우팅 설명용이지 논문 실험의 매개변수가 아니다.

두 색 작업에는 type-1도 들어가므로, 같은 색의 삼각형은 여러 두 색 작업에서 다시 발견될 수 있다. 원문 알고리즘 1의 절차만으로 *중복 없는 목록 출력*을 증명했다고 읽지 않는다. 논문의 문제 정의는 각 삼각형에 대한 로컬 열거 호출을 허용하고, 정리 1은 필요한 삼각형을 모두 찾는다는 보장으로 읽는 것이 안전하다.

## 수식으로 읽는 공간·작업량 보장

### 기본 CTTP: 기대값과 전체 공간

$$\rho\asymp\sqrt{E/m}$$개의 색을 $$R\asymp\rho E/M$$개의 라운드에 분산하면, 정리 1의 라운드 차수는

$$
R=O\!\left(\frac{E^{3/2}}{M\sqrt{m}}\right).
$$

한 매퍼의 간선 전달량은 라운드당 $$\Theta(\rho/R)=\Theta(M/E)$$ 규모이고, 한 리듀서는 세 색상 간선 집합을 받는다. 정리 1은 리듀서 하나의 공간을 **기대값으로** $$m$$, 전체 합산 공간을 $$M$$, 기대 총 작업량을 $$O(E^{3/2})$$로 제시한다. 4-wise independent 색칠은 임의의 고정 입력 그래프에 대한 기대 분석을 가능하게 하지만, 불운한 색칠에서도 모든 리듀서가 $$m$$ 안에 들어간다는 결정적 보장은 아니다.

원문은 설명을 위해 차수가 $$\sqrt{Em}$$보다 큰 정점이 없다고 두고 분석한다. 그러한 정점에 닿는 삼각형은 정렬 기반 절차로 별도 처리할 수 있으며, 원문 3.2절은 적절한 $$m$$ 조건 아래 이 전처리도 CTTP와 같은 점근 라운드·작업량에 포함된다고 설명한다. 이 단계 없이 모든 그래프의 색상 부하가 균등하다고 가정해서는 안 된다.

### 하한: 왜 최악 경우 라운드 차수가 맞는가

정리 2는 간선·정점 하나가 적어도 한 메모리 워드를 차지한다는 비분할성 가정 아래의 용량 논증이다. 크기 $$m_i\le m$$인 한 리듀서가 열거할 수 있는 서로 다른 삼각형은 많아야 $$O(m_i^{3/2})$$개다. 한 라운드에서 $$\sum_i m_i\le M$$이므로,

$$
\sum_i m_i^{3/2}\le\sqrt{m}\sum_i m_i\le M\sqrt{m}.
$$

즉, 삼각형이 $$t$$개인 입력에는 적어도 $$\lfloor t/(M\sqrt{m})\rfloor$$라운드가 필요하다는 하한을 얻는다. 완전 그래프 계열에는 $$t=\Theta(E^{3/2})$$가 가능하므로 CTTP의 라운드 차수와 맞는다. 이것은 해당 $$MR(m,M)$$ 모델과 메모리 가정에서의 **최악 경우 점근 최적성**이지 모든 희소 그래프·시스템에서 가장 빠르다는 의미가 아니다.

### 고확률 변형: 마지막 리듀서 위험 다루기

정리 3은 기본형의 4-wise 색칠을 그대로 반복한 결과가 아니다. 차수 $$\sqrt{Em}$$ 초과 정점에 닿는 삼각형을 먼저 별도 처리한 뒤, 차수 $$\sqrt E$$ 이하 정점에는 $$\log E$$-wise independent 해시를 사용한다. 그보다 차수가 큰 정점은 색마다 차수 합이 균형을 이루도록 결정적으로 배치한다. 이 변형에서

$$
m=\Omega\!\left(E^{3/4}\sqrt{\log E}\right)
$$

이면 임의의 고정 상수 $$\varepsilon>0$$에 대해 확률이 적어도 $$1-1/E^{\varepsilon}$$일 때 **각 리듀서 공간이 $$O(m)$$이고 총 작업량이 $$O(E^{3/2})$$**다. 매퍼 공간 $$O(M/E)$$, 전체 공간 $$O(M)$$와 라운드 차수 $$O((E/M)\lceil\sqrt{E/m}\rceil)$$도 유지한다. 추가 메모리 조건과 색칠·고차수 처리를 빼고 이 고확률 결론만 가져올 수는 없다.

## 실험 설정과 결과

저자들은 Java/Hadoop으로 CTTP, TTP, GP를 비교했다. 2014년 KAIST 클러스터는 40대, 머신당 RAM 4GB였고 기본 리듀서 수는 80이었다. 입력은 방향·중복 간선과 자기 루프를 제거해 단순 무방향 그래프로 만들었으며, 세 방법에 공통인 전처리 시간은 실행 시간 비교에서 제외했다. 주요 실험은 $$M=E$$를 가정해 큰 입력에서 $$R=\rho$$로 두되, 라운드별 작업 수가 리듀서 수보다 적은 작은 입력에는 $$R=1$$을 사용했다.

### 라운드 수: 한 번의 shuffle 피크와 반복 비용

논문의 비용 모델에서 라운드당 전달 데이터는 대략 $$(\rho-1)E/R$$이다. 라운드를 늘리면 **동시에** 쌓이는 데이터가 줄지만, 모든 라운드를 합친 작업별 간선 전달과 반복 입력 읽기가 없어지지는 않는다. Twitter 라운드 실험에서는 $$R=1$$일 때 shuffle 데이터가 985GB로, 해당 실험의 입력 파일 32GB보다 약 30배 컸다. 원문 그림 1-2에서 $$R<4$$의 실행 시간은 단순 비용 모델 예상보다 길었고, map·shuffle 병목이 두드러졌다. 반대로 큰 $$R$$에서는 라운드 시작과 전체 입력 재독 비용이 누적되며, $$R>62$$에서는 작업 수가 리듀서 수보다 적어 자원을 모두 쓰지 못한다. 따라서 라운드를 무조건 늘리는 것이 답은 아니다.

### 데이터·머신 확장성과 실제 그래프

YahooWeb에서 간선을 무작위 선택해 2억, 4억, 8억, 16억, 32억, 64억 간선 부분 그래프를 만든 실험(원문 그림 3)에서 CTTP는 보고된 모든 크기를 처리했다. TTP와 GP는 **16억 간선을 초과한** 부분 그래프에서 공간 부족 오류를 냈다. 이는 CTTP의 라운드 분산이 그 클러스터에서 중간 데이터 피크를 낮춘 관측이며, 다른 환경에서도 동일한 간선 수가 실패 임계값이라는 뜻은 아니다. Twitter의 10-80 리듀서 실험(그림 4)에서는 CTTP가 세 방법 중 이상적인 속도 향상 선에 가장 가까웠다. GP는 10 리듀서에서 공간 부족으로 실패했으므로 속도 향상 기준은 20 리듀서였다.

ClueWeb09에서는 전처리 후 79억 간선과 31,013,037,486개 삼각형에 대해 CTTP만 1,328분에 완료했다(원문 표 2·그림 5). 다만 이 수치는 `enum(·)` 호출을 허용하는 문제 정의의 열거 결과이며, 310억 개의 결과 레코드를 모두 영구 저장했다는 증거가 아니다. 또한 원문 결론의 PhoneCall `2×` 표현은 그림 5(b)의 분 단위 표(CTTP 6분, TTP 6분, GP 11분)만으로는 확인되지 않는다. 이 글은 비교 조건과 표 수치를 우선 제시한다.

## 논문의 핵심 기여와 해석 포인트

첫째, TTP식 색상 작업을 여러 라운드에 배치해 전체 시스템 공간 $$M$$과 라운드 수의 절충을 명시했다. 둘째, 무작위 **입력 그래프**를 전제하는 대신 4-wise independent **색칠의 무작위성**으로 임의의 고정 그래프에 대한 기대 경계를 분석했다. 셋째, 같은 모델의 삼각형 출력 용량 하한과 라운드 차수를 맞췄다. 넷째, 차수별 색칠을 결합한 변형에서 마지막 리듀서에 대한 고확률 경계를 별도 조건으로 제시했다.

읽을 때는 세 가지를 구별하는 것이 유용하다. **라운드당 피크** 감소는 **전체 간선 전달량** 감소와 다르다. **기대 리듀서 크기**는 **모든 리듀서의 확정적 상한**이 아니다. **모든 삼각형 발견**도, 두 색 작업에서 재발견될 수 있는 type-1까지 포함하면, **중복 없는 영구 출력 파일**과 같은 요구가 아니다.

## 한계와 향후 과제

논문의 고확률 보장은 기본형 전체에 자동 적용되지 않고, 차수별 처리와 $$m=\Omega(E^{3/4}\sqrt{\log E})$$를 요구한다. 한 라운드의 피크를 낮추는 대신 입력을 매 라운드 다시 읽으므로 라운드 시작·디스크 I/O 비용이 남는다. 실험은 2014년 Hadoop 클러스터와 선정된 실제 그래프에서 얻은 값이어서 현대 분산 시스템의 절대 성능이나 같은 메모리 임계값을 예측하지 않는다. 또한 문제 정의는 로컬 열거 호출을 허용하므로 결과의 전역 중복 제거, 영속 저장, 출력 파일 크기 관리는 이 보장만으로 해결되지 않는다. 후속 구현을 평가한다면 이러한 출력 정책과 실제 리듀서별 최대 부하를 별도로 측정해야 한다.

## 한국어 번역형 해설

### 초록과 서론의 논지

삼각형은 그래프의 국소 연결 구조를 드러내지만, 거대한 그래프를 한 번에 처리하려면 입력 간선의 여러 사본이 네트워크와 디스크로 몰린다. 기존 MapReduce 연구가 라운드 수를 줄이는 데 집중했다면, 이 논문은 라운드를 늘려도 한 번에 필요한 중간 데이터가 시스템 공간 한도 안에 머물게 할 수 있는지를 묻는다. 따라서 성능을 단순 실행 시간 하나가 아니라 라운드 수, 리듀서별 공간, 전체 공간, 총 작업량으로 나누어 평가한다.

### 방법과 분석의 논지

CTTP는 정점을 색상 그룹으로 나누어 삼각형을 두 색 또는 세 색 부분 문제에서 찾는다. 모듈러 색상 합은 각 부분 문제의 실행 순서를 정하고, 매퍼는 그 시점에 필요한 간선만 보낸다. 이 구조 덕분에 한 라운드에서 필요한 사본 수는 줄지만, 뒤 라운드를 위해 원본을 다시 읽는다. 기본 정리는 무작위 색칠에 대한 평균적 부하를, 하한 정리는 한 라운드가 물리적으로 열거할 수 있는 삼각형 수를 설명한다. 마지막 리듀서가 예외적으로 무거워지는 위험은 별도의 고확률 변형에서 다룬다.

### 실험의 논지

Twitter 실험은 적은 라운드가 중간 데이터 피크를 키우고 실제 map·shuffle을 느리게 만들 수 있음을 보여 준다. YahooWeb 부분 그래프 실험은 큰 입력에서 한 라운드식 경쟁 방식이 공간 부족으로 멈춘 반면 CTTP는 완료한 사례다. 실제 그래프 시간표에서도 CTTP가 대체로 앞서지만 LiveJournal과 PhoneCall에서는 TTP와 분 단위 기록이 같다. 그러므로 `모든 경우 2배 빠름`이 아니라, 그래프 크기와 공간 병목이 있는 조건에서 분산 효과가 크게 나타났다고 읽는 편이 정확하다.

### 결론의 적용 범위

논문의 핵심은 총 계산을 없애는 새로운 삼각형 정의가 아니라, 주어진 $$m,M$$ 안에서 이미 필요한 색상별 계산을 여러 시점으로 나누는 설계다. 기대값, 고확률, 최악 경우 하한은 서로 다른 문장과 조건을 가진다. 실험은 그 설계가 당시의 큰 그래프에서 유용했음을 뒷받침하지만, 결과 저장 방식과 다른 실행 환경의 비용은 별도로 정해야 한다.

## 마지막 핵심 정리

**CTTP의 실질적인 이득은 전체 작업을 삭제하는 것이 아니라 한 라운드의 중간 데이터 피크를 제어하는 데 있다.** 기본형의 리듀서 메모리는 기대값 보장이고, 모든 리듀서의 고확률 $$O(m)$$ 경계에는 더 강한 색칠과 메모리 조건이 필요하다. 실험 수치는 2014년 Hadoop 구성과 로컬 열거 정의에 묶어 읽어야 한다.
