# LS05 Lists

Source PDF: `LS05_lists_full.pdf`

|---|---|---|

| 2 | 리스트 개념 | 순서가 있는 데이터 모음은 어떤 연산을 제공하는가? |

## 1. 리스트란?

리스트는 순서가 있는 데이터의 나열이다. 각 원소는 리스트 안에서 자신의 위치, 즉 인덱스를 가진다.

```text
index: 0   1   2   3
value: 10  20  30  40
```

리스트는 단순히 값을 모아 둔 것이 아니라, **위치 기반 접근**을 제공한다는 점이 중요하다.

## 2. 리스트의 주요 연산

| 연산 | 의미 |
|---|---|
| 탐색 Search | 특정 인덱스 또는 특정 값을 가진 원소를 찾는다. |
| 갱신 Update | 특정 위치의 원소를 새 값으로 교체한다. |
| 삽입 Insert | 원하는 위치에 새 원소를 추가한다. |
| 삭제 Delete | 특정 위치의 원소를 제거한다. |
| 순회 Traverse | 모든 원소를 차례대로 읽는다. |

스택, 큐, 데크 같은 선형 자료구조는 리스트를 제한하거나 확장해서 구현할 수 있다.

## 3. List ADT

List ADT는 구현 방법과 상관없이 "위치를 가진 원소들의 유한 순서열"을 정의한다.

ADT 관점에서는 배열을 쓰는지, 연결 리스트를 쓰는지 알 필요가 없다. 사용자는 `get`, `insert`, `remove` 같은 연산이 어떤 의미를 갖는지만 알면 된다.

| 관점 | 질문 |
|---|---|
| ADT | 리스트로 무엇을 할 수 있는가? |
| 자료구조 | 리스트를 메모리에 어떻게 배치할 것인가? |

## 4. 배열 기반 리스트 구현

배열 기반 리스트는 보통 두 정보를 가진다.

| 구성 요소 | 역할 |
|---|---|
| 배열 | 실제 원소를 저장하는 고정 크기 공간 |
| `size` 변수 | 현재 저장된 원소 개수 |

`size`가 필요한 이유는 배열의 전체 용량과 실제 원소 개수가 다를 수 있기 때문이다.

```text
capacity = 8
size = 4

[10, 20, 30, 40, _, _, _, _]
```

순회할 때는 배열 전체가 아니라 `0`부터 `size - 1`까지만 읽어야 한다.

## 5. 배열 기반 리스트의 연산 복잡도

| 연산 | 시간 복잡도 | 이유 |
|---|---|---|
| 인덱스 탐색 | `O(1)` | 인덱스로 바로 접근할 수 있다. |
| 특정 값 탐색 | `O(n)` | 앞에서부터 비교해야 한다. |
| 갱신 | `O(1)` | 인덱스를 알고 있으면 바로 바꾼다. |
| 삽입 | `O(n)` | 뒤 원소들을 한 칸씩 밀어야 한다. |
| 삭제 | `O(n)` | 뒤 원소들을 한 칸씩 당겨야 한다. |
| 순회 | `O(n)` | 모든 원소를 한 번씩 읽는다. |

배열 기반 리스트의 핵심 장점은 빠른 임의 접근이고, 핵심 단점은 중간 삽입/삭제 시 원소 이동 비용이다.

## 6. 장단점 해석

| 장점 | 설명 |
|---|---|
| 인덱스 접근이 빠름 | `list[i]`를 바로 찾을 수 있다. |
| 구현이 단순함 | 포인터 관리가 필요 없다. |
| 캐시 친화적 | 메모리에 연속 저장되어 CPU 캐시 효율이 좋다. |

| 단점 | 설명 |
|---|---|
| 삽입/삭제가 느림 | 중간 위치에서는 원소 이동이 필요하다. |
| 크기가 고정됨 | 용량 초과 시 재할당이 필요하다. |
| 메모리 낭비 가능 | 실제 원소보다 큰 배열을 잡으면 빈 공간이 생긴다. |

## 시험 포인트

| 질문 | 답의 방향 |
|---|---|
| 배열 기반 리스트에서 인덱스 접근이 빠른 이유는? | 연속 메모리와 인덱스 계산으로 바로 접근하기 때문 |
| 삽입/삭제가 `O(n)`인 이유는? | 원소를 밀거나 당겨야 하기 때문 |
| `size` 변수는 왜 필요한가? | 실제 저장된 원소 개수를 관리하기 위해 |
| 특정 값 탐색이 `O(n)`인 이유는? | 값은 어디 있는지 모르므로 순차 탐색해야 한다. |

## 복습 질문

<details>
<summary>1. 배열 기반 리스트에서 맨 끝 삽입은 항상 `O(1)`인가? 용량이 부족하면 어떻게 되는가?</summary>

답변: 빈 공간이 있으면 맨 끝 삽입은 `O(1)`이다. 하지만 용량이 부족하면 더 큰 배열을 새로 만들고 기존 원소를 복사해야 하므로 그 순간에는 `O(n)` 비용이 든다.

</details>

<details>
<summary>2. `capacity`와 `size`의 차이는 무엇인가?</summary>

답변: `capacity`는 배열이 확보한 전체 저장 공간이고, `size`는 현재 실제로 저장된 원소 개수다. 순회나 삭제 판단은 보통 `capacity`가 아니라 `size`를 기준으로 해야 한다.

</details>

<details>
<summary>3. 중간 삽입이 많은 프로그램에서 배열 기반 리스트가 불리한 이유는 무엇인가?</summary>

답변: 중간에 새 원소를 넣으려면 그 뒤의 원소들을 한 칸씩 뒤로 밀어야 하기 때문이다. 이 원소 이동 때문에 삽입 위치에 따라 `O(n)` 시간이 걸릴 수 있다.

</details>

## Study Notes

리스트는 "순서가 있는 원소들의 모음"이다. 여기서 순서가 있다는 말은 각 원소가 위치를 가진다는 뜻이다. 배열 기반 리스트는 이 위치를 인덱스로 직접 계산할 수 있기 때문에 `get(i)`가 빠르다.

배열 기반 리스트의 내부 상태는 보통 다음처럼 이해하면 된다.

```text
capacity = 8
size     = 5

index: 0   1   2   3   4   5   6   7
value: 10  20  30  40  50  _   _   _
```

`capacity`는 확보한 전체 공간이고, `size`는 실제로 사용하는 원소 수다. 순회, 삽입, 삭제는 항상 `size`를 기준으로 해야 한다. `capacity`까지 순회하면 아직 유효하지 않은 빈칸을 데이터처럼 다루는 오류가 생긴다.

중간 삽입은 원소 이동이 핵심이다.

```text
insert index 2, value 99

before: [10, 20, 30, 40, 50, _, _, _]
move:   [10, 20, 30, 30, 40, 50, _, _]
after:  [10, 20, 99, 30, 40, 50, _, _]
```

실제로는 뒤에서부터 한 칸씩 밀어야 한다. 앞에서부터 밀면 기존 값이 덮여 사라질 수 있다.

삭제는 반대로 뒤 원소들을 앞으로 당긴다.

```text
remove index 2

before: [10, 20, 30, 40, 50]
after:  [10, 20, 40, 50, _]
```

맨 끝 삽입은 빈 공간이 있을 때는 `O(1)`이다. 하지만 배열이 꽉 찼다면 더 큰 배열을 새로 만들고 기존 원소를 복사해야 한다. 동적 배열에서는 이 비용을 amortized analysis로 다루지만, 이 강의에서는 배열 기반 리스트의 기본 원리와 원소 이동 비용을 먼저 이해하는 것이 중요하다.

## When to Use

| 상황 | 배열 기반 리스트가 적합한가? |
|---|---|
| 인덱스로 자주 읽는다. | 적합 |
| 맨 뒤에 주로 추가한다. | 대체로 적합 |
| 중간 삽입/삭제가 매우 많다. | 부적합 |
| 메모리를 연속적으로 쓰고 싶다. | 적합 |
| 데이터 크기 변화가 매우 크다. | 재할당 비용을 고려해야 함 |
