# LS08 Doubly Linked Lists and Dictionaries

Source PDF: `LS08_dll_dictionary.pdf`

> **핵심:** **단일 연결 리스트와 이중 연결 리스트의 차이는** 이중 연결 리스트는 `prev`와 `next`를 모두 가진다. **이중 연결 리스트 삽입 시 갱신해야 할 포인터는** 새 노드의 `prev/next`, 주변 노드의 `next/prev`.

## 전체 흐름

| 순서 | 주제 | 핵심 질문 |
|---|---|---|
| 1 | 스택/큐 구현 복습 | 비어 있는 경우와 마지막 원소 삭제는 어떻게 처리하는가? |
| 2 | 단방향 선형 구조 | 배열, 연결 리스트, 스택, 큐는 왜 한 방향적 성격을 갖는가? |
| 3 | 이중 연결 리스트 | `prev`와 `next`를 함께 쓰면 무엇이 좋아지는가? |
| 4 | 딕셔너리 | 인덱스가 아니라 key로 값을 찾는 구조는 무엇인가? |
| 5 | 해시 충돌 | 딕셔너리의 평균 $$O(1)$$은 언제 깨질 수 있는가? |

## 1. 스택과 큐 구현에서 중요한 예외 처리

이 강의는 이전 강의에서 비워 둔 스택/큐 코드의 핵심 처리도 복습한다.

| 구조 | 핵심 처리 |
|---|---|
| ArrayStack | `pop()`은 `--top` 후 반환, `topValue()`는 `top - 1` 반환 |
| LinkedStack | `pop()` 후 `top = top.next`, `size--` |
| ArrayQueue | `front = (front + 1) % capacity` |
| LinkedQueue | 마지막 노드 삭제 시 `rear = null` |

시험에서 코드 빈칸이 나오면 "현재 포인터/인덱스가 무엇을 의미하는가"를 먼저 확인해야 한다.

## 2. 단방향 선형 구조

배열, 단일 연결 리스트, 스택, 큐는 모두 선형 자료구조다. 데이터가 일렬로 배치되고 접근 흐름이 비교적 일정하다.

| 구조 | 단방향적 성격 |
|---|---|
| 배열 | 앞에서 뒤로 순차 탐색하는 경우가 많다. |
| 단일 연결 리스트 | `next`만 있어 뒤로만 이동한다. |
| 스택 | `top` 한쪽 끝에서만 접근한다. |
| 큐 | `rear`에서 삽입하고 `front`에서 삭제한다. |

## 3. 이중 연결 리스트

이중 연결 리스트는 각 노드가 이전 노드와 다음 노드를 모두 가리킨다.

```java
private static class Node<E> {
    E item;
    Node<E> prev;
    Node<E> next;
}
```

| 필드 | 의미 |
|---|---|
| `prev` | 이전 노드 |
| `next` | 다음 노드 |

이 구조는 양방향 탐색이 가능하고, 특정 노드를 알고 있을 때 그 노드의 앞뒤 연결을 더 쉽게 바꿀 수 있다.

## 4. 이중 연결 리스트 삽입

`A`와 `B` 사이에 `X`를 넣는다고 생각하면 네 연결을 맞춰야 한다.

```text
A <-> B

A <-> X <-> B
```

필요한 갱신은 다음과 같다.

```java
X.prev = A;
X.next = B;
A.next = X;
B.prev = X;
```

단, 맨 앞이나 맨 뒤 삽입에서는 `head`, `tail`, `null` 처리가 추가된다.

## 5. 이중 연결 리스트 삭제

`A <-> X <-> B`에서 `X`를 삭제하려면 `A`와 `B`를 직접 이어 준다.

```java
A.next = B;
B.prev = A;
```

삭제 대상이 `head`나 `tail`이면 각각 `head = head.next`, `tail = tail.prev` 형태의 처리가 필요하다.

## 6. 이중 연결 리스트 장단점

| 장점 | 설명 |
|---|---|
| 양방향 탐색 | 앞뒤로 이동할 수 있다. |
| 삭제/삽입 유연성 | 특정 노드를 알고 있으면 앞뒤 연결을 쉽게 바꿀 수 있다. |
| `tail` 활용 | 뒤쪽 작업이 더 자연스럽다. |

| 단점 | 설명 |
|---|---|
| 메모리 증가 | 노드마다 `prev` 포인터가 추가된다. |
| 구현 복잡성 | 삽입/삭제 시 갱신할 포인터가 많다. |
| 예외 처리 증가 | 빈 리스트, 맨 앞, 맨 뒤 처리가 중요하다. |

## 7. 딕셔너리 Dictionary

딕셔너리는 데이터를 key-value 쌍으로 저장하는 구조다.

```text
key       value
"2025001" -> "Alice"
"2025017" -> "Cindy"
```

리스트가 위치나 인덱스로 원소를 찾는다면, 딕셔너리는 key로 value를 찾는다.

| 연산 | 의미 |
|---|---|
| `put(key, value)` | key-value 쌍 삽입 또는 기존 값 수정 |
| `get(key)` | key에 해당하는 value 탐색 |
| `remove(key)` | key-value 쌍 삭제 |
| `contains(key)` | key 존재 여부 확인 |

## 8. 딕셔너리의 특징

| 특징 | 설명 |
|---|---|
| key는 유일 | 같은 key는 하나만 존재한다. |
| value는 중복 가능 | 여러 key가 같은 value를 가질 수 있다. |
| 평균 탐색 $$O(1)$$ | 해시 함수를 통해 key를 배열 인덱스로 바꾼다. |
| 순서 없음 | 일반적으로 삽입 순서나 정렬 순서를 보장하지 않는다. |
| 충돌 가능 | 서로 다른 key가 같은 인덱스로 갈 수 있다. |

충돌이 많아지면 삽입, 삭제, 탐색이 최악의 경우 $$O(n)$$까지 느려질 수 있다.

## Study Guide

이중 연결 리스트 삽입·삭제는 새 노드와 양쪽 이웃의 prev/next 네 연결을 그림에 표시한 뒤 한 줄씩 코드로 옮긴다. dictionary는 위치가 아니라 unique key로 value를 찾으며 value 자체는 중복될 수 있다는 점을 리스트와 대비한다. 해시 기반 평균 O(1)은 충돌이 적다는 조건부 주장이고 최악 O(n)도 가능하다는 문장이 시험 핵심이다.

## 복습 질문

<details markdown="block">
<summary>1. `A <-> B` 사이에 `X`를 넣을 때 포인터 네 개를 어떤 순서로 바꾸는가?</summary>

답변: `X.prev = A`, `X.next = B`, `A.next = X`, `B.prev = X`로 연결한다. 핵심은 새 노드가 양쪽 노드를 가리키고, 양쪽 노드도 새 노드를 가리키게 만드는 것이다.

</details>

<details markdown="block">
<summary>2. 딕셔너리에서 key는 중복될 수 있는가?</summary>

답변: key는 중복될 수 없다. 같은 key를 다시 넣으면 보통 새 항목을 추가하는 것이 아니라 기존 key의 value를 갱신한다. value는 중복될 수 있다.

</details>

<details markdown="block">
<summary>3. 딕셔너리가 순서를 유지하지 않는다는 말은 정렬된 출력이 필요할 때 어떤 의미를 갖는가?</summary>

답변: 일반적인 해시 기반 딕셔너리는 key의 정렬 순서를 보장하지 않는다. 따라서 정렬된 출력이 필요하면 key를 따로 정렬하거나, 처음부터 트리 기반 맵처럼 순서를 유지하는 자료구조를 사용해야 한다.

</details>

## Study Notes

### 복잡도 주장의 조건 확인

> **분류:** stack/queue 복습과 dictionary 비용에 대한 **불변식·조건부 분석**이다.
>
> **원문 추적:** Source PDF 10--20쪽의 stack/queue 복잡도 표와 원형 큐 코드, 25--31쪽의 이중 연결 리스트 연산, 35--38쪽의 dictionary 연산·특징을 대조한 보충 해설이다.

용량 $$C>0$$인 원형 배열 큐는 `rear`와 `front`를 각각 $$(x+1)\bmod C$$로 갱신한다. 나머지는 항상 $$0,\ldots,C-1$$ 범위라 배열 끝 다음이 0으로 이어진다. 별도 `size`를 둔다면 $$0\le\mathrm{size}\le C$$, empty는 `size == 0`, full은 `size == C`가 불변식이다. `front == rear`만으로 두 상태를 모두 나타내면 구분할 수 없으므로 한 칸을 비우거나 flag가 필요하다.

여기서 $$n$$은 저장 원소 수, $$C$$는 배열 용량이며 둘 다 무차원 개수다. 이중 연결 리스트에서 삭제할 노드 참조를 이미 알고 있으면 `prev.next`, `next.prev` 등 상수 개의 링크만 바꾸므로 $$\Theta(1)$$이다. 반면 key로 노드를 먼저 찾아야 하면 최대 $$n$$개 노드를 지나므로 탐색이 $$\Theta(n)$$일 수 있다. 해시 dictionary의 평균 $$O(1)$$ 역시 좋은 분산과 낮은 충돌을 가정한 조건부 결론이며, 모든 key가 한 슬롯에 모이면 체인이나 probe를 $$n$$개 확인해 최악 $$\Theta(n)$$이다.

이중 연결 리스트는 단일 연결 리스트의 약점을 줄이기 위해 각 노드가 이전 노드와 다음 노드를 모두 기억한다.

```text
null <- [A] <-> [B] <-> [C] -> null
```

이 구조의 장점은 뒤로도 이동할 수 있다는 점이다. 특정 노드를 이미 알고 있다면 그 앞뒤의 연결을 더 쉽게 바꿀 수 있다. 단점은 노드마다 `prev` 포인터가 하나 더 필요하고, 삽입/삭제 시 갱신해야 할 포인터가 많아진다는 점이다.

중간 삽입은 네 연결을 맞춰야 한다.

```text
A <-> B 사이에 X 삽입

X.prev = A
X.next = B
A.next = X
B.prev = X
```

중간 삭제도 양쪽을 서로 직접 연결한다.

```text
A <-> X <-> B 에서 X 삭제

A.next = B
B.prev = A
```

단, 삭제 대상이 첫 노드이거나 마지막 노드라면 `head`, `tail`, `null` 처리를 따로 확인해야 한다. 그래서 실제 구현에서는 sentinel node를 두어 예외를 줄이는 경우도 많다.

딕셔너리는 연결 리스트와 관점이 다르다. 리스트는 위치 중심이고, 딕셔너리는 key 중심이다. 사용자는 몇 번째 위치에 있는지보다 "이 key에 연결된 value가 무엇인가"를 묻는다.

```text
studentId -> studentName
word      -> meaning
url       -> cachedPage
```

딕셔너리는 보통 해시 테이블로 구현되어 평균 $$O(1)$$ 탐색을 목표로 한다. 하지만 이 평균 성능은 충돌이 적고 해시 함수가 값을 고르게 분산시킨다는 조건 위에 있다.

## Common Pitfalls

| 실수 | 올바른 이해 |
|---|---|
| 이중 연결 리스트 삽입에서 `prev`만 바꾼다. | 양쪽 노드의 `next`, `prev`를 모두 맞춰야 한다. |
| key와 value가 모두 유일하다고 생각한다. | key는 유일하지만 value는 중복될 수 있다. |
| 딕셔너리를 항상 정렬된 구조로 생각한다. | 일반적인 해시 기반 딕셔너리는 정렬 순서를 보장하지 않는다. |
| 평균 $$O(1)$$을 최악 $$O(1)$$로 이해한다. | 충돌이 심하면 최악 $$O(n)$$도 가능하다. |
