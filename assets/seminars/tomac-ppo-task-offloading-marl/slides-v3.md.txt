# TOMAC-PPO: 작업 단위로 학습하는 MEC 오프로딩

논문: A Task Offloading and Resource Allocation Strategy Based on Multi-Agent Reinforcement Learning in Mobile Edge Computing

저자: Guiwen Jiang, Rongxi Huang, Zhiming Bao, Gaocai Wang (2024)

## 1. TOMAC-PPO: 작업 단위로 학습하는 MEC 오프로딩

동기화, 이동성 대응, 작업 지향 MDP와 PPO를 하나의 제어 구조로 연결한다


근거: [paper](https://doi.org/10.3390/fi16090333) title, abstract, publication record

## 2. 용어: 계산 위치와 학습 단위를 먼저 구분한다


| 용어 | 풀어 쓰기 | 이 발표에서의 역할 |
| --- | --- | --- |
| MEC | Mobile Edge Computing | 단말 근처 서버 계산 |
| MDP | Markov Decision Process | 상태·행동·보상의 틀 |
| MARL | Multi-Agent Reinforcement Learning | 여러 대표 노드의 학습 |
| Actor / Critic | 정책망 / 가치망 | 행동 선택 / 가치 추정 |
| TOMAC-PPO | Task-Oriented Multi-Agent Collaborative–PPO | 작업 단위 공동 결정 |

핵심: PPO는 Proximal Policy Optimization; 정책을 갱신하는 방법이다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 2, 9–13, 19, §4 and abbreviations

## 3. 오프로딩과 자원 배분은 하나의 결정 문제다

실행 위치만 정해도 CPU, 통신, queue의 경쟁은 남는다

1. **작업 생성**: 크기·기한·종류가 다름
2. **실행 위치**: 단말·엣지·클라우드·폐기
3. **자원 배분**: CPU·대역폭·대기 순서
4. **결과 평가**: 지연·에너지·폐기 비용

핵심: 실행 위치와 자원 비율을 따로 최적화하면 실제 queue와 통신 경쟁을 놓칠 수 있다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 1–2, Introduction; pp. 7–8, Eq. 13

## 4. 논문의 기여와 검증 범위

방법은 여러 구성 요소를 결합하지만 검증은 Python simulation에 한정된다


| 구성 | 논문이 제안한 내용 | 검증 경계 |
| --- | --- | --- |
| system | 계층·대기열·장애 모델 | 실제 deployment가 아님 |
| coordination | 주기 동기화·이동 후 결과 반환 | 통신 overhead 측정 없음 |
| decision | subnet별 Actor–Critic agent | global optimality 증명 없음 |
| time | 작업별로 겹치는 MDP step | credit assignment 보장 없음 |
| learning | Transformer + PPO | Transformer ablation 없음 |

핵심: 제안 구조와 시뮬레이션 결과를 실제 배포 성능 보장과 구분한다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 1–2, contributions; p. 18, limitations

## 5. 경로 예: 이웃 엣지를 거쳐 클라우드로

가능한 전달 경로 하나다. 가까운 엣지에서 끝나거나 코어망으로 바로 전달할 수도 있다

- **레인 사용자 계층**
- **레인 edge 계층**
- **레인 cloud 계층**
  - **Mobile task**: data → deadline → type
  - **가까운 edge node**: base station과 server
  - **인접 edge node**: routing table로 연결
  - **Cloud server**: core network 경유
- Mobile task → 가까운 edge node (실선, 단방향)
- 가까운 edge node → 인접 edge node (실선, 단방향)
- 인접 edge node → Cloud server (실선, 단방향)

핵심: offload target은 한 edge에 한정되지 않으며 이웃 edge와 cloud도 후보가 된다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 3–4, Fig. 1, §3.1

## 6. 작업은 단말 실행·엣지 실행·전달 경로로 갈라진다

엣지에 도착한 작업을 실행할지 다른 서버로 전달할지 구분한다

- **레인 단말 실행**
- **레인 엣지 실행**
- **레인 다른 서버로 전달**
  - **단말 캐시**: 결정 대기
  - **단말 계산 큐**: 실행 대기
  - **단말 결과**: 단말 CPU 실행
  - **단말 전송 큐**: 업로드 대기
  - **엣지 도착**: 선택된 경로로 분기
  - **엣지 계산 큐**: CPU 실행 대기
  - **엣지 결과**: 이후 사용자로 반환
  - **유선 전송 큐**: 다른 서버행
  - **목적 서버 실행**: 이후 결과 반환
- 단말 캐시 → 단말 계산 큐 (실선, 단방향)
- 단말 계산 큐 → 단말 결과 (실선, 단방향)
- 단말 캐시 → 단말 전송 큐 (실선, 단방향)
- 단말 전송 큐 → 엣지 도착 (실선, 단방향)
- 엣지 도착 → 엣지 계산 큐 (실선, 단방향)
- 엣지 계산 큐 → 엣지 결과 (실선, 단방향)
- 엣지 도착 → 유선 전송 큐 (실선, 단방향)
- 유선 전송 큐 → 목적 서버 실행 (실선, 단방향)

핵심: 다른 서버로 보낼 작업은 엣지 계산 큐를 먼저 거치지 않는다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 3–5, Fig. 2, §3.2

## 7. 네 task type은 비용에서 강조하는 항이 다르다

같은 policy가 모든 task에 같은 지연·에너지 trade-off를 적용하지 않는다


| type | 요구 | phi1 지연 | phi2 에너지 | drop |
| --- | --- | --- | --- | --- |
| high-priority | 짧은 지연과 완료 | 사용 | 0 | 포함 |
| critical | 폐기 억제 요구 | 0 | 0 | 포함 |
| low-priority | 에너지 절감 | 0 | 사용 | 포함 |
| routine | 세 비용을 종합 | 1 | 1 | 포함 |

핵심: task type은 label에 그치지 않고 Eq. 11의 비용 가중치를 바꾼다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 5, 7, §3.3 and Eq. 11

## 8. Action의 weight는 실제 자원 share로 정규화된다

agent가 직접 GHz나 MHz를 출력하지 않고 같은 server의 weight 합으로 나눈다


| 자원 | action weight | 실제 배분 | 함께 경쟁하는 대상 |
| --- | --- | --- | --- |
| 엣지 CPU | ff | ff / Σff × f_edge | 같은 엣지의 실행 작업 |
| 무선 대역폭 | bf | bf / Σbf × B | 같은 기지국의 사용자 |
| 큐 우선순위 | qf | 큰 값이 앞선다 | 같은 큐의 작업 |
| 큐 임계값 | thmin, thmax | 수용·확률 폐기·폐기 | 새 작업 |

핵심: 개별 weight의 효과는 다른 사용자와 task가 낸 weight에 따라 달라진다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 4–6, Eqs. 2–3 and queue rules

## 9. 가중치 예시: 값 자체보다 경쟁자와의 비율이 중요하다

설명용 가정: CPU 총 처리량6, 대역폭20; 두 경쟁자의 가중치를 정규화한다


| 상황 | 가중치 | 정규화 | 배분 |
| --- | --- | --- | --- |
| CPU A / B | .2 / .3 | .2/.5, .3/.5 | 2.4 / 3.6 |
| CPU B만 증가 | .2 / .8 | .2/1, .8/1 | 1.2 / 4.8 |
| 대역폭 U / V | .25 / .75 | .25/1, .75/1 | 5 / 15 MHz |
| A의 관점 | 자기 .2는 그대로 | B가 커지면 A 비율 감소 | A 계산은 더 느려짐 |

핵심: A의 action이 그대로여도 B의 행동과 새 작업 도착이 A의 자원 몫을 바꾼다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 5–6, Eqs. 2–3

## 10. 큐 제어: 우선순위와 새 작업의 수용 여부는 다르다

가상 임계값 thmin=4, thmax=8로 원문의 세 구간을 읽는다


| 관측 또는 행동 | 예 | 처리 | 역할 |
| --- | --- | --- | --- |
| 낮은 혼잡 | 평균 큐 길이3 | 새 작업 수용 | 진입 허용 |
| 중간 혼잡 | 평균 큐 길이6 | 확률적으로 폐기 | 혼잡 완화 |
| 상한 도달 | 큐 길이8 | 새 작업 폐기 | 용량 보호 |
| 수용된 작업 | qf=.8 vs .3 | .8을 앞에 배치 | 실행 대기 순서 |

핵심: 큰 qf가 폐기 면제나 CPU 배분량을 직접 의미하지는 않는다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 4–5, queue rules; p. 15, Table 1

## 11. 실행 경로마다 지연·단말 에너지 항이 다르다

전송, 전파, 계산, core forwarding을 경로에 맞게 더한다


| 항 | 원문 계산 | 의미 |
| --- | --- | --- |
| 계산 | T = λρ/f | 입력량×계산 밀도/처리량 |
| 단말↔엣지 | T = λ/C + d/Vspace | 무선 전송과 전파 |
| 엣지↔엣지 | T = λ/Cfiber + d/Vfiber | 인접 엣지 사이 |
| 엣지↔클라우드 | T = 전송 + 전파 + core 지연 | 코어망 전달 포함 |
| 단말 에너지 | κλρf_user² 또는 P_user×T | 단말 계산 또는 업로드 |

핵심: offload는 local CPU를 아끼지만 통신 지연과 전송 에너지를 새로 만든다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 6–7, Eqs. 5–10, §3.5

## 12. 작업 비용: 지연·에너지·폐기를 합한다

Eq. 11의 각 항은 크기가 다른 측정값을 비교 가능한 형태로 묶는다


| 항 | 식 | 읽는 법 | 주의 |
| --- | --- | --- | --- |
| delay | phi1 × Ttotal/deadline | Ttotal > deadline이면 지각 | type에 따라 제외 |
| energy | phi2 × Etotal/(mu1 λρ) | 0–1로 정규화 | mu1 값은 미제시 |
| drop | drop ∈ {0,1} | discard이면 1 | 모든 type에 남음 |
| total | Z(x) = delay + energy + drop | 작을수록 유리 | 장기 합을 최소화 |

핵심: 비용의 절대 크기보다 같은 normalization과 task type 아래의 비교가 중요하다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 7, Eqs. 11–12, §3.6

## 13. 공동 최적화가 선택하는 변수와 지켜야 할 조건

논문은 긴 시간의 task cost 합을 줄이는 constrained problem을 세운다


| 범주 | 내용 | 대표 조건 |
| --- | --- | --- |
| offloading D | local·edge·cloud·drop 중 하나 | 각 task에 정확히 한 결과 |
| resource ff, bf | CPU weight와 bandwidth weight | 각 weight는 0부터 1 |
| 대기 순서 qf | 작업 우선순위 가중치 | 단말·엣지 용량 제한 |
| deadline | task total delay | Ttotal은 deadline 이하 |
| coverage | user와 edge 거리 | base-station radius 이하 |

핵심: learned action의 목적은 Eq. 13 전체의 장기 비용을 낮추는 것이다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 7–8, Eq. 13 and C1–C9

## 14. 요구조건·감점·실제 충족은 같은 뜻이 아니다


| 층위 | 원문 | 읽어야 할 범위 |
| --- | --- | --- |
| 문제의 요구 | 기한·용량·범위 제약 | Eq13의 최적화 목표 |
| 학습의 감점 | PEN∈{0,1}을 보상에서 뺌 | 유한한 비용 신호 |
| Critical 요구 | 폐기하면 안 됨 | 작업 유형의 설계 요구 |
| 실험 결과 | Critical drop = 5.50% | 무폐기를 달성한 것은 아님 |

핵심: 제약 위반에 감점을 주었다는 사실만으로 모든 행동의 제약 준수를 증명할 수 없다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 5, 7, 11, 17, Eq13/16 and Fig13

## 15. 주기 동기화가 local observation을 보완한다

단말·엣지·클라우드의 주기 보고와 미수신 timeout 규칙을 묶어 본다


| 통신 대상 | 주기적으로 공유하는 정보 | 해석 |
| --- | --- | --- |
| 단말 → 엣지 | 단말의 현재 위치 | 이동 상태 갱신 |
| 엣지 ↔ 인접 엣지 | 상태·연결 정보 | 경로 정보 유지 |
| 클라우드 ↔ 엣지 | 연결 상태 | 연결 확인 |
| 미수신 처리 | 동기화 주기를 넘는 timeout | 연결 끊김 판정·재전송 없음 |

핵심: policy state의 network view는 실시간 전역 관측이 아니라 주기적으로 동기화된 정보다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 8, Fig. 3, §4.1

## 16. 이동 사용자 scheduling의 앞부분

task summary로 먼저 결정하고 실제 data는 결정 뒤에 보낸다

1. **1. summary 보고**: user가 가까운 decision node에 task 정보를 전송
2. **2. decision 반환**: node가 network 상태를 보고 offload 결과 계산
3. **3. 실행 시작**: user가 local 계산 또는 task data 전송

핵심: 초기 signaling과 실제 task-data 전송은 서로 다른 단계다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 8–9, Fig. 4, §4.2, steps 1–3

## 17. 이동 사용자 scheduling의 반환 경로

실행 중 user가 cell을 바꾸면 결과는 현재 위치에 가까운 node로 돌아온다

1. **4. target 전달**: decision node가 선택된 실행 node로 task 전송
2. **5. return 선택**: 실행 node가 현재 user에 가까운 node를 찾음
3. **6. 결과 전달**: shortest path 뒤 return node가 user에게 전송

핵심: 결정을 내린 node, 실행 node, 결과를 돌려주는 node가 서로 다를 수 있다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 9, Fig. 4, §4.2, steps 4–6

## 18. Subnet마다 commentator node 하나가 agent가 된다

ordinary node의 관측과 실행을 subnet 대표 edge가 모아 결정한다

- **레인 정책·작업 처리**
- **레인 대표 노드 학습**
  - **일반 노드 관측**: 큐·연결·위치
  - **노드별 정책들**: 실행할 action 선택
  - **가치망**: 가치 추정
  - **전달된 action**: 위치·자원·큐
  - **작업 처리 종료**: 보상·완료 관측
  - **학습 갱신**: 파라미터 갱신
- 일반 노드 관측 → 노드별 정책들 (실선, 단방향)
- 일반 노드 관측 → 가치망 (실선, 단방향)
- 노드별 정책들 → 전달된 action (실선, 단방향)
- 전달된 action → 작업 처리 종료 (실선, 단방향)
- 가치망 → 학습 갱신 (실선, 단방향)
- 작업 처리 종료 → 학습 갱신 (실선, 단방향)

핵심: 전체 network가 한 agent인 구조도, 모든 edge가 독립 agent인 구조도 아니다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 9, Fig. 5, §4.3

## 19. 분산 실행과 지역 중앙집중의 경계

지역별 대표 노드의 결정 구조이며 전역 중앙 학습기나 파라미터 평균을 가정하지 않는다


| 질문 | 원문이 말하는 것 | 원문이 말하지 않는 것 |
| --- | --- | --- |
| agent 단위 | subnet의 commentator node | 엣지마다 독립 agent 아님 |
| ordinary node | 관측 제출 후 action 실행 | 자기 policy로 결정하지 않음 |
| critic | commentator 내부 value network | 전역 critic은 미제시 |
| 병렬성 | Algorithm 1의 agent loop | 파라미터 평균은 미제시 |
| cloud 역할 | 계산 후보와 connectivity 확인 | 전체 정책 학습기 아님 |

핵심: TOMAC-PPO의 분산성은 subnet 간 결정 분리에 있다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 9, §4.3; p. 13, Algorithm 1

## 20. 고정 global slot 대신 task마다 다른 step을 둔다

처리 시간이 다른 task를 같은 clock tick에 맞추지 않는다


| 구분 | 고정 시간 slot | TOMDP task step |
| --- | --- | --- |
| 시작 | 모든 system이 같은 경계 | 각 task 생성 시점 |
| 종료 | 정해진 slot 끝 | 해당 task 완료 시점 |
| 길이 | 일정 | task 처리 시간에 따라 다름 |
| 동시성 | 한 global tick으로 표현 | 여러 task step이 겹침 |
| reward | slot 단위로 설계 | task 완료 뒤 feedback |

핵심: TOMDP의 핵심은 task lifecycle과 transition의 경계를 맞추는 것이다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 10, Fig. 6, §4.4

## 21. Task step은 서로 겹치고 완료 순서도 바뀔 수 있다

설명용 사건 순서: A 생성 → B 생성 → B 완료 → A 완료; 축은 실제 시간 단위가 아니다

- **레인 Task A**
- **레인 Task B**
  - **A 생성**: step A 시작
  - **A action**: 긴 처리
  - **A 완료**: reward A
  - **B 생성**: step B 시작
  - **B action**: 짧은 처리
  - **B 완료**: reward B
- A 생성 → A action (실선, 단방향)
- A action → A 완료 (실선, 단방향)
- B 생성 → B action (실선, 단방향)
- B action → B 완료 (실선, 단방향)

핵심: 각 작업의 생성·관측·완료 시점을 서로 구분한다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 10, Fig. 6, §4.4

## 22. TOMDP state는 task와 연결 가능한 network를 함께 본다

Eq. 14는 tensor shape보다 정보 범주를 읽는 것이 안전하다


| 범주 | state 항 | 의미 |
| --- | --- | --- |
| task | 정규화 λ, deadline, task type | 처리량과 중요도 |
| mobility | user coordinate records H_i | edge가 저장한 위치 |
| user queue | 단말의 세 큐 합 / R_ud | 단말의 혼잡 |
| edge queue | 엣지 두 큐 합 / R_en | 선택 edge의 혼잡 |
| network | Link_j, thmin, thmax, j/n | 연결과 queue control |

핵심: 한 agent의 state는 local observation과 동기화로 얻은 연결 node 정보의 결합이다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 10, Eq. 14, §4.4 Status

## 23. TOMDP action은 위치와 네 종류의 control을 묶는다

Eq. 15의 한 action이 실행 경로와 자원 경쟁을 동시에 바꾼다


| action 항 | 결정 | system에 미치는 영향 |
| --- | --- | --- |
| D | local·edge·cloud·drop | 실행 경로 |
| ff | CPU allocation weight | edge compute delay |
| qf | queue priority weight | 대기 순서 |
| bf | bandwidth weight | uplink rate |
| thmin, thmax | queue thresholds | accept와 drop policy |

핵심: 행동은 실행 위치뿐 아니라 CPU·대역폭·큐 제어를 함께 포함한다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 10–11, Eq. 15, §4.4 Action

## 24. Reward는 현재 task cost를 user 평균과 비교한다

Zavg는 사용자 평균 작업 비용이다. Z/Zavg가 작을수록 보상이 커지고 PEN=1이면 1을 뺀다


| 항 | 값 | 역할 |
| --- | --- | --- |
| 기본 상수 | 1 + 1/2 | reward의 기준점을 1.5로 둔다 |
| 상대 cost | Z / Zavg | 현재 task가 평균보다 비싼지 비교 |
| constraint | PEN(x) ∈ {0,1} | initial decision 위반을 감점 |
| 전체 | R = 1.5 − Z/Zavg − PEN | task 완료 뒤 계산 |

핵심: reward는 절대 latency가 아니라 task type이 반영된 정규화 cost를 사용한다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 11, Eq. 16, §4.4 Rewards

## 26. 한 task가 하나의 learning transition이 되는 순서

action과 reward 사이의 실제 처리 시간을 task step 안에 포함한다

1. **관측 시점**: 요약·네트워크 상태 관측
2. **정책 결정**: 실행 위치·가중치 선택
3. **동시 처리**: 다른 작업과 자원 공유
4. **처리 종료**: 해당 작업의 결과 확정
5. **학습 자료**: 보상·완료 상태 연결

핵심: reward delay를 없애는 것이 아니라 어느 task action에 연결할지 명시한다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 10–11, Fig. 6 and Eqs. 14–16

## 27. 같은 state가 policy와 value의 두 network로 들어간다

policy는 action probability를, value network는 state value 하나를 출력한다

- **레인 policy**
- **레인 value**
  - **State s(x)**: task → queues → links
  - **Transformer + 3 FC**: policy feature 계산
  - **Transformer + 3 FC**: value feature 계산
  - **Softmax output**: 행동 확률
  - **Scalar value**: v(s;ω)
- State s(x) → Transformer + 3 FC (실선, 단방향)
- State s(x) → Transformer + 3 FC (실선, 단방향)
- Transformer + 3 FC → Softmax output (실선, 단방향)
- Transformer + 3 FC → Scalar value (실선, 단방향)

핵심: policy와 value는 출력 목적이 다르며 target value network는 value 구조를 복제한다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 11–12, Figs. 7–8, §4.5

## 28. Transformer: 구조의 위치와 미제시 세부

논문이 명시한 구조와 구현에 필요한 미제시 항목을 분리한다


| 구분 | 명시됨 | 미제시 |
| --- | --- | --- |
| 목적 | state memory와 prediction을 지원 | prediction target과 평가 지표 |
| 위치 | state 뒤, FC layers 앞 | encoder·decoder 세부 |

| sequence | state s가 입력 | history 길이와 token 구성 |

## 29. PPO는 확률을 강제 고정하지 않고 학습 목적식을 자른다

엔트로피를 잠시 제외하면 J = min(ratio×Adv, clip(ratio,0.8,1.2)×Adv)


| 기호 | 정의 | 역할 |
| --- | --- | --- |
| ratio_t | π_new(a_t\|s_t) / π_old(a_t\|s_t) | action probability 변화 |
| zeta | clip 반경, Table 1은 0.2 | 목적식 안의 clip 구간 |
| Adv_t | Qπ(s_t,a_t) − Vπ(s_t) | action이 기대보다 좋은 정도 |
| clip term | clip(ratio, 1−zeta, 1+zeta) × Adv | surrogate 증가 제한 |
| entropy | cH(s_t;θ), c=0.01 | exploration을 장려 |

핵심: 실제 ratio가 구간 밖으로 갈 수 있다; clip은 확률 변화의 강제 상한이 아니다

근거: [paper](https://doi.org/10.3390/fi16090333) pp. 12–13, Eqs. 17–18 and Fig. 9

## 32. Algorithm 1의 training loop

각 subnet agent가 trajectory를 모으고 policy와 value를 갱신한다

1. **초기화**: 정책·가치·target 가치망
2. **Episode**: 학습 회차 반복
3. **Agent별 수집**: 각 정책으로 T-step 수집
4. **정책 갱신**: Adv 계산 후 목적식 상승
5. **가치망 갱신**: 가치·target 가중치 갱신

핵심: Algorithm 1에는 global parameter server나 agent 간 gradient averaging이 없다

근거: [paper](https://doi.org/10.3390/fi16090333) p. 13, Algorithm 1 and Eqs. 19–23

## 42. TOMAC-PPO를 한 흐름으로 다시 읽기

network coordination과 task lifecycle을 먼저 정의한 뒤 PPO가 joint action을 학습한다

1. **상태 공유**: 위치·연결을 주기 보고
2. **지역 대표**: subnet별로 대신 결정
3. **작업 단위**: 생성·관측·완료 구분
4. **공동 행동**: 위치·자원·큐 제어
5. **학습**: 종료 보상으로 갱신

핵심: 이 논문의 핵심은 PPO 하나보다 task, network, time의 경계를 함께 설계한 데 있다

근거: [paper](https://doi.org/10.3390/fi16090333) abstract; pp. 8–18, §§4–6
