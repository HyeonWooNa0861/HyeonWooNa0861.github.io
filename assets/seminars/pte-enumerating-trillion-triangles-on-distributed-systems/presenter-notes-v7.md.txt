# PTE 세미나 발표자 노트

## 1. PTE: 대규모 그래프의 삼각형 열거

**슬라이드 목적:** 논문의 질문과 발표 범위를 한 문장으로 제시한다.

**발표 대본:**  
안녕하세요. 오늘 소개할 논문은 2016년 KDD에 발표된 **PTE, Pre-partitioned Triangle Enumeration**입니다. 이 논문은 “수십억 개의 정점과 간선을 가진 그래프에서 어떻게 모든 삼각형을 찾아낼 것인가?”라는 질문에서 시작합니다. 오늘은 복잡한 증명보다, 기존 방식이 어디에서 막혔고 PTE가 데이터 흐름을 어떻게 바꾸었는지에 초점을 맞추겠습니다. 먼저 여기서 말하는 삼각형 열거가 무엇인지부터 보겠습니다.

**교육 포인트:** PTE의 약어를 “미리 분할한 삼각형 열거”라고 풀어 준다.

**근거:** PTE (KDD 2016), p. 1. DOI: 10.1145/2939672.2939757

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 2. Triangle enumeration의 의미

**슬라이드 목적:** counting과 enumeration을 구분하고, 논문의 정확한 문제 정의를 전달한다.

**발표 대본:**  
그래프의 삼각형은 세 정점이 서로 모두 연결된 구조입니다. **Triangle counting**이 전체 개수만 구하는 문제라면, **triangle enumeration**은 각각의 삼각형을 하나씩 발견하는 문제입니다. 논문은 자기 루프와 중복 간선이 없는 무방향 단순 그래프를 가정합니다. 같은 삼각형을 여러 번 찾지 않도록 정점을 degree, 즉 연결 수가 작은 순서로 두고, degree가 같으면 ID 순서로 정합니다. 이 순서가 간선의 실제 방향을 바꾸는 것은 아니고, 중복 계산을 피하기 위한 표기 규칙입니다. 또 중요한 점은 발견한 3조 개의 삼각형을 모두 파일에 저장해야 한다는 뜻이 아니라는 것입니다. 각 삼각형을 찾을 때 로컬 `enum` 함수를 호출해 바로 집계하거나 검사할 수 있습니다. 그렇다면 어려움은 최종 결과의 크기만이 아니라, 결과를 찾는 동안 생기는 데이터에도 있습니다.

**교육 포인트:** “개수만 세기”와 “각 항목을 발견해 콜백에 전달하기”를 손으로 하나, 둘 세는 비유로 구분한다.

**근거:** PTE §1, §3.1, Definition 1, pp. 1, 3. A/B/C는 설명용 예시.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 3. 그래프가 커질 때 생기는 병목

**슬라이드 목적:** 문제 규모를 수치와 자원에 연결한다.

**발표 대본:**
ClueWeb12에는 약 63억 정점과 720억 간선이 있고 삼각형은 약 3.06조 개입니다. 입력 파일이 큰 것뿐 아니라, 찾는 과정에서 복사하는 데이터와 최종 결과도 커집니다. 여기서 RAM은 지금 계산할 부분을, 디스크는 입력과 임시 파일을, 네트워크는 장비 사이의 이동을 담당합니다. 논문의 약 70TB는 모든 삼각형을 결과 파일로 보존할 때의 규모입니다. 메모리라는 말이 어디에서는 RAM이고 어디에서는 디스크인지 혼동하기 쉬우므로 다음 장에서 먼저 구분하겠습니다.

**교육 포인트:** 숫자를 외우기보다 입력·중간 데이터·결과가 각각 커진다는 흐름을 강조한다.

**근거:** PTE §2.1, p. 2; Table 2, p. 8. 3,064,499,157,291개 triangle.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 4. External memory는 RAM이 아니다

**슬라이드 목적:** RAM, external memory, output storage를 분리한다.

**발표 대본:**
책상과 책장을 떠올려 봅시다. 지금 펼쳐 놓고 계산하는 책상이 RAM이고, 아직 펼치지 않은 자료를 넣어 두는 책장이 SSD나 HDD입니다. 이 논문에서 external memory는 RAM 밖의 저장장치이지 RAM 자체가 아닙니다. 저장장치가 본체 안에 들어 있어도 메모리 계층에서는 external이라고 부릅니다. 책상보다 큰 자료는 책장에서 조금씩 꺼내 처리할 수 있지만, 필요한 입력과 작업 파일이 책장 전체 용량보다도 크면 놓을 곳이 없습니다. 결과 저장공간은 또 다른 문제입니다. 약 3.06조 개 삼각형을 각각 64-bit 정점 ID 세 개로 단순 저장하면 24바이트씩 약 73.5TB입니다. 이는 저장 형식을 가정한 계산이지 압축된 모든 표현의 보편적 하한은 아닙니다. 논문의 약 70TB와 같은 규모지만, RAM을 70TB 요구한다는 뜻은 아닙니다. 결과를 enum 함수에 넘겨 바로 집계하고 버리면 결과 전체를 보존하지 않아도 됩니다.

**교육 포인트:** RAM 부족 → 70TB 생성이라는 인과관계가 아니다. 입력·임시 파일과 출력 보관은 서로 다른 저장 요구다.

**근거:** PTE §2.1, p. 2; Definition 1, p. 3. 64-bit ID 세 개를 저장하는 교육용 계산.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 5. 입력보다 중간 데이터가 더 커지는 이유

**슬라이드 목적:** 왜 입력 크기만 보고 처리 가능성을 판단할 수 없는지 설명한다.

**발표 대본:**
중심 한 명이 다른 백만 명과 연결되어 있지만 이웃끼리는 연결되지 않은 별 모양 그래프를 생각해 봅시다. 간선은 백만 개이고 삼각형은 없습니다. 그런데 이웃 두 명의 모든 조합을 후보로 만들면 백만 곱하기 99만 9999를 2로 나눈 약 5천억 개가 됩니다. 정답이 없어도 후보가 폭증할 수 있는 것입니다. 모든 알고리즘이 이 후보를 저장하는 것은 아닙니다. 이 예시는 후보를 물질화하는 방식의 위험을 보여 줍니다. PTE와 직접 연결되는 또 다른 문제는 같은 간선을 여러 부분 문제에 복제하는 것입니다. 복제본은 mapper 메모리만 차지하는 것이 아니라 임시 디스크, 네트워크, reducer의 병합과 정렬을 거칩니다. 따라서 서버의 RAM을 더한다고 모든 병목이 자동으로 사라지지 않습니다.

**교육 포인트:** 후보 폭증과 TTP의 간선 복제는 중간 데이터가 커지는 서로 다른 경로다. 모든 방식에 같은 실패 원인을 씌우지 않는다.

**근거:** PTE §2.2-2.4, pp. 2-3. 별 모양 그래프와 후보 수는 교육용 예시.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 6. 기존 알고리즘의 접근과 한계

**슬라이드 목적:** 단일 머신, 분산 메모리, MapReduce 계열을 PTE의 문제의식으로 연결한다.

**발표 대본:**  
기존 접근은 크게 세 종류입니다. I/O-efficient 알고리즘은 RAM보다 큰 그래프를 디스크에서 처리하지만 단일 머신의 저장공간과 반복 I/O가 한계입니다. GraphLab이나 GraphX 같은 분산 메모리 방식은 간선과 정점을 여러 머신에 복제하므로 중간 복제본이 분산 RAM을 넘을 수 있습니다. MapReduce의 GP와 TTP는 정점에 임의의 색을 주고 작은 부분 문제로 나눕니다. 그러나 각 간선을 여러 reducer 입력에 반복해서 보내기 때문에 shuffle 양이 간선 수보다 훨씬 빠르게 늘어납니다. CTTP는 한 번에 처리하는 양을 제한하도록 여러 round로 쪼개 공간 부족 부담을 낮추지만, 전체적으로는 같은 간선을 계속 shuffle하고 매 round마다 데이터셋을 읽습니다. PTE가 바꾸려는 핵심은 삼각형 탐색법 자체보다 이 비효율적인 데이터 이동 구조입니다. TTP가 GP를 상수 계수만큼 개선했다는 말의 뜻부터 짚고 색 분할로 넘어가겠습니다.

**교육 포인트:** 데이터 이동 관점에서는 CTTP가 한 번에 나르는 짐을 줄인다고 설명한다. 단 CTTP는 4-wise-independent 색 배정과 부하 분석도 포함하며, PTEBASE의 pairwise 가정과 동일하지 않다. 이것만으로 매번 메모리 수용이 확정되는 것은 아니다.

**근거:** PTE §2.1-2.4, pp. 2-3; §3.2, p. 4. 논문이 검토한 방법 기준.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757) · [공개 출처 3](https://www.dei.unipd.it/~silvestri/assets/publications/PSKP14.pdf)

## 7. GP 대비 TTP의 Constant-factor 개선

**슬라이드 목적:** GP와 TTP의 실제 간선 복제 횟수로 constant-factor 개선의 의미와 비교 조건을 설명한다.

**발표 대본:**
여기서 비교하는 비용은 mapper가 reducer로 보내는 간선 레코드의 개수입니다. 입력 간선 수를 m, 색 수를 ρ라고 하고 두 방법에 같은 ρ를 사용합니다. 정점의 색은 균등 무작위로 배정하며 GP의 세 색 작업을 정의할 수 있도록 ρ는 3 이상입니다. 색 라벨과 색 조합별 작업은 다음 슬라이드에서 설명합니다.

GP는 서로 다른 세 색을 고른 작업에 간선을 보냅니다. 간선 양 끝의 색이 같으면 나머지 두 색을 ρ-1개 중에서 고르므로 간선당 (ρ-1)(ρ-2)/2개의 레코드가 생깁니다. 양 끝의 색이 다르면 나머지 한 색을 고르므로 ρ-2개입니다. TTP는 triangle type에 맞게 두 색 작업과 세 색 작업을 구분합니다. 같은 색 간선은 두 색 작업 ρ-1개에 보내고, 다른 색 간선은 두 색 작업 1개와 세 색 작업 ρ-2개에 보냅니다. 따라서 TTP는 어느 종류의 간선이든 정확히 ρ-1개의 레코드를 만듭니다.

균등하고 독립적인 끝점 색 배정에서 같은 색 간선일 확률은 1/ρ, 다른 색일 확률은 (ρ-1)/ρ입니다. 이를 GP의 복제 횟수에 가중하면 전체 기대 레코드 수는 3m(ρ-1)(ρ-2)/(2ρ)입니다. TTP는 색 배정 결과와 무관하게 m(ρ-1)개입니다. 두 식의 차이는 m(ρ-1)(ρ-6)/(2ρ)이므로, 같은 ρ에서 TTP의 레코드 수가 GP의 기대값보다 작은 조건은 ρ > 6입니다. ρ=6이면 같으며 3부터 5까지는 이 레코드 수 기준으로 TTP가 더 작지 않습니다.

ρ가 커지면 GP의 기대 비용은 약 1.5mρ, TTP는 약 mρ입니다. TTP / E[GP]는 2/3에 가까워지므로 약 1/3 적은 레코드를 보내지만 두 방법 모두 Θ(mρ)입니다. 입력 크기에 따른 증가 차수를 유지하면서 앞의 상수 계수를 줄인다는 뜻입니다. 이는 동일한 색 수에서의 분석이며, 같은 reducer 메모리 조건에서 색 수를 각각 조절하는 비교에 이 절감률을 그대로 적용할 수는 없습니다. 또한 레코드 개수는 정확한 전송 byte 수나 전체 실행시간과 구별해야 합니다. 실제 시간에는 계산, 디스크 I/O, 정렬과 네트워크가 함께 작용합니다. PTE는 사전 분할로 shuffle을 O(m)으로 줄이지만, 이것이 전체 연산이나 모든 network read까지 선형으로 만든다는 뜻은 아닙니다.

**교육 포인트:** 같은 ρ와 균등 색 배정이라는 비교 조건을 먼저 명시한다. GP는 기대값, TTP는 정확한 레코드 수다. 약 1/3 절감은 큰 ρ에서의 레코드 수 분석이며 모든 ρ나 실행시간에 적용되는 고정 개선율이 아니다.

**근거:** TTP §4.1-4.3, Lemma 2·Theorem 2, pp. 4-6; PTE §2.4·§3.2, pp. 3-4. m=간선 수, ρ=색 수. 공개 원논문의 map-output 레코드 분석이며 가상 비용이나 실행시간 측정값이 아니다.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757) · [공개 출처 3](https://islab.kaist.ac.kr/chungcw/InterConfPapers/km0805-ha-myung.pdf)

## 8. 분할 기준 1: 정점에 색 라벨을 붙인다

**슬라이드 목적:** 정점에 색을 배정하는 실제 기준을 명확히 한다.

**발표 대본:**
분할은 먼저 정점에 라벨을 붙이는 데서 시작합니다. 정점 v를 입력으로 받는 함수 ξ를 무작위 해시 함수 집합에서 하나 선택합니다. 선택한 함수는 0부터 ρ−1 사이의 색을 반환하고 실행 동안 모든 작업이 같은 함수를 씁니다. 같은 정점을 다른 간선에서 만났다고 다시 색을 뽑으면 안 됩니다. 서로 다른 A와 B가 모두 0을 받아도 두 정점이 합쳐지는 것은 아닙니다. 학생 두 명이 같은 색 이름표를 단 것과 같습니다. 이 라벨은 같은 주제나 커뮤니티를 찾은 결과가 아니고 차수가 비슷한 정점을 묶은 것도 아닙니다. 색의 개수 ρ는 머신 수와 같다고 정하지 않고 간선 수와 가용 RAM으로 정합니다. 논문이 특정한 해시 API나 seed, ID 나머지 연산을 지정한 것은 아니므로 여기서 임의 구현을 논문 알고리즘으로 소개하지 않겠습니다.

**교육 포인트:** 한 실행에서 함수는 고정된다. 무작위 선택과 결정적인 함수 평가를 구분한다.

**근거:** PTE Table 1, p. 2; §3.2-4.1, pp. 3-4. A/B/C의 색 배정은 설명용 예시.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 9. 색상으로 나누는 세 가지 triangle type

**슬라이드 목적:** 공통 배경인 세 triangle type을 기존 질문의 혼동과 연결한다.

**발표 대본:**
앞에서 붙인 색 라벨로 삼각형을 세 종류로 분류합니다. 세 정점과 세 간선이 이미 존재하는 삼각형을 전제로 합니다. A, B, C가 모두 같은 색이면 type-1, 정확히 두 정점만 같은 색이면 type-2, 셋 다 다른 색이면 type-3입니다. 같은 색이 된다는 것은 정점 자체가 같아진다는 뜻이 아닙니다. 또 인접한 정점이 서로 다른 색이어야 하는 proper graph coloring 문제도 아닙니다. 이 색 분류는 TTP에서 사용하고 CTTP와 PTE도 활용하는 공통 배경입니다. 이 슬라이드만 보고 CTTP의 고유 동작이라고 이해하면 부족합니다. 색 배정을 바꾸면 같은 삼각형의 type은 바뀔 수 있지만 원래 간선이나 삼각형의 존재는 바뀌지 않습니다.

**교육 포인트:** 이름표만 바뀐다. 같은 색이라고 새 간선이 생기지 않는다.

**근거:** PTE §3.2, p. 3; §4.1, p. 4. 그림은 정의를 설명하는 자체 제작 개념도.

## 10. 분할 기준 2: 색 조합이 하나의 작업이 된다

**슬라이드 목적:** 정점 분할과 작업 분할을 연결한다.

**발표 대본:**
작업은 색 조합으로 정합니다. 두 색 작업 (i,j)은 i 내부, j 내부, i와 j 사이의 간선을 모아 type-1과 type-2를 찾습니다. 세 색 작업 (i,j,k)은 서로 다른 색 사이의 세 묶음만 모아 type-3를 찾습니다. 예를 들어 A와 B가 0, C가 1인 기존 삼각형은 (0,1) 작업이 담당합니다. A,B 사이 내부 간선과 A,C 및 B,C 사이의 간선을 함께 읽으면 됩니다. 세 정점 색이 0,1,2라면 (0,1,2) 작업이 필요합니다. 존재하는 모든 두 색 조합과 세 색 조합을 처리하므로 한 머신이 여러 작업을 차례로 맡을 수 있습니다. 색 하나를 머신 한 대와 동일시하지 마세요. Type-1은 여러 두 색 작업에 포함되므로 PTEBASE는 지정된 작업에서만 출력하고 PTECD는 중복 계산까지 줄입니다.

**교육 포인트:** 두 색 작업에도 내부 간선이 필요하다. 원래 TTP counting의 가중치 보정과 PTE enumeration의 출력 규칙은 같지 않다.

**근거:** PTE §3.2-4.1, pp. 3-5. 색 번호와 A/B/C는 설명용 예시.

## 11. 분할 기준 3: 간선 파일은 끝점 색의 순서로

**슬라이드 목적:** 실제 저장 키의 순서와 설명용 묶음의 차이를 보인다.

**발표 대본:**
앞에서 두 색 사이의 간선을 모아 작업한다고 했습니다. 이때 색 0인 정점과 색 1인 정점을 잇는 모든 간선의 집합을 E01이라고 부릅니다. E는 간선 집합을 뜻하고 0과 1은 색 라벨입니다. 정점 ID가 0과 1인 간선 하나를 뜻하는 것도, 새로운 간선을 만드는 것도 아닙니다.

이 논리적 집합과 실제 저장 파일은 구분합니다. 먼저 정점은 차수가 작은 순서로, 동률이면 ID 순서로 정렬합니다. 예시에서 이 순서가 A, C, B이고 색은 A와 B가 0, C가 1이라고 합시다. 각 간선을 이 정점 순서대로 한 번만 기록하므로 실제 간선 (A,C)는 E_star[0,1]에, (C,B)는 E_star[1,0]에 들어갑니다. 색 번호를 작은 것부터 다시 정렬하지 않는 것입니다. 두 파일은 같은 간선의 복사본이 아니라 서로 겹치지 않는 집합입니다. 색 0과 1 사이의 간선을 모두 읽으려면 두 파일을 함께 읽어야 하므로 E01 = E_star[0,1] ∪ E_star[1,0]입니다. 여기서 ∪는 합집합 기호이며, E01이라는 새 파일을 따로 저장해야 한다는 뜻은 아닙니다. 같은 색 내부의 E00은 E_star[0,0] 하나입니다.

따라서 정점 순서는 차수와 ID, 실제 파일 키는 순서 있는 끝점 색, 작업 키는 사용할 두 색이나 세 색의 조합이라는 세 층을 구분해야 합니다. 예시는 삼각형 밖의 이웃까지 포함한 전체 그래프의 차수에 의해 A, C, B 순서가 성립할 수 있다고 가정합니다.

**교육 포인트:** E_star의 별표는 곱셈이 아니라 집합 표기의 구별이다. 순서 없는 E와 순서 있는 E_star를 섞지 않는다.

**근거:** PTE Table 1, §3.1, §4.1, Algorithm 1, pp. 2-4. E_star는 원문의 E*를 읽기 쉽게 쓴 표기.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 12. TTP에서는 간선 하나가 여러 작업으로 복제된다

**슬라이드 목적:** 분할 수 증가가 왜 복제 비용을 늘리는지 직접 센다.

**발표 대본:**
색이 네 개일 때 TTP의 간선 하나를 따라가 봅시다. 양 끝 색이 모두 0이면 이 간선은 (0,1), (0,2), (0,3) 두 색 작업에 각각 필요합니다. 양 끝 색이 0과 1이면 (0,1) 작업에 한 번, (0,1,2)와 (0,1,3) 작업에 두 번 필요합니다. 두 경우 모두 세 레코드가 됩니다. 일반적으로 ρ개 색이면 같은 색 간선은 ρ−1개의 두 색 작업으로 가고, 다른 색 간선은 한 두 색 작업과 ρ−2개의 세 색 작업으로 갑니다. 그래서 총 복제 레코드는 (ρ−1)m입니다. CTTP는 이 작업들을 여러 round로 나누어 한 번의 부담을 낮춥니다. 하지만 전체 round를 합하면 같은 복제 레코드들을 보내고 입력도 round마다 다시 읽습니다. 이 표는 TTP 내부의 복제를 센 예시이지 ρ=4에서 GP보다 적다는 비교가 아닙니다.

**교육 포인트:** 작게 쪼개는 이익과 더 많이 복사하는 비용이 동시에 생긴다. CTTP의 공간 제어 효과 자체는 유효하다.

**근거:** PTE §2.4, §3.2, pp. 3-4; CTTP (CIKM 2014), §4, §5.3. 네 색은 교육용 예시.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757) · [공개 출처 3](https://www.dei.unipd.it/~silvestri/assets/publications/PSKP14.pdf) · [공개 출처 4](https://islab.kaist.ac.kr/chungcw/InterConfPapers/km0805-ha-myung.pdf)

## 13. PTEBASE: 분할 저장과 열거의 분리

**슬라이드 목적:** pre-partitioning이 shuffle 복제를 선행 분할과 선택 읽기로 바꾸는 원리를 설명한다.

**발표 대본:**  
PTEBASE의 핵심은 이름 그대로 **pre-partitioning**, 즉 미리 분할하는 것입니다. 첫 단계에서 각 간선을 양 끝 정점의 색 조합에 따라 정확히 하나의 간선 파일에 저장합니다. 예를 들어 색이 i와 j인 정점을 잇는 간선은 해당 색과 순서에 맞는 파일에 한 번만 들어갑니다. 이 단계의 shuffle 양은 간선 수에 선형인 `O(|E|)`입니다. 다음 열거 단계에서는 reducer를 위해 부분 그래프를 다시 만들어 보내지 않습니다. 각 map 작업이 분산 저장소에서 자기 부분 문제에 필요한 간선 파일만 읽어 메모리에서 삼각형을 찾습니다. CTTP가 매 round마다 전체 데이터를 읽고 간선을 여러 부분 문제로 다시 배송한다면, PTEBASE는 한 번 분류해 창고에 두고 각 작업이 필요한 상자만 가져오는 구조입니다. 다만 shuffle이 선형이 되었다고 전체 비용이 모두 선형인 것은 아닙니다. 필요한 파일을 여러 부분 문제에서 읽는 network read와 실제 이웃 비교 작업은 여전히 남습니다. 그래서 PTE는 BASE에서 끝나지 않고 계산과 읽기 순서를 두 단계 더 개선합니다. 그 전에 분할 크기를 평균적으로 조절하는 이유와 색 수를 정하는 기준을 보겠습니다.

**교육 포인트:** “한 번 분류해 저장”과 “작업마다 필요한 파일을 선택해서 읽기”를 두 단계로 끊어 말한다.

**근거:** PTE Algorithms 1-2, §4.1, pp. 4-5; Hadoop 구현 §4.5, p. 7.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 14. Pairwise independence: 왜 평균적으로 퍼질까?

**슬라이드 목적:** pairwise independence가 기대값 분석을 가능하게 하는 이유와 한계를 설명한다.

**발표 대본:**
색 하나를 균등하게 뽑아 모든 정점에 같은 색을 주면, 각 정점의 색은 균일하게 분포하지만 간선은 한 파일에 몰립니다. 따라서 정점 하나의 색이 균일한 것만으로는 부족하고 두 정점 사이 독립성도 필요합니다. 간선은 서로 다른 두 끝점으로 결정됩니다. 색이 세 개라면 특정한 순서 있는 색상쌍이 될 확률은 1/3 곱하기 1/3, 즉 1/9입니다. 간선 900개 각각의 확률을 더하면 한 E_star 파일의 기대 간선 수는 100개입니다. 이 기대값의 합을 계산할 때 간선끼리 모두 독립적일 필요는 없습니다. 같은 중심 정점을 공유하는 간선들은 그 정점 색을 함께 사용하므로 배정이 연관될 수 있습니다.

여기서 E01의 뜻을 다시 확인합니다. E01은 색 0인 정점과 색 1인 정점을 잇는 간선 전체이며, 실제 저장 파일 E_star[0,1]과 E_star[1,0]의 합집합입니다. 두 파일에 각각 기대상 100개가 있고 서로 겹치는 간선이 없으므로 E01의 기대 크기는 100 + 100 = 200개입니다. 확률로도 서로 배타적인 (0,1)과 (1,0) 두 경우를 더해 1/9 + 1/9 = 2/9가 됩니다. 반면 색 0 내부의 E00은 (0,0)이라는 한 경우만 있으므로 E_star[0,0] 하나, 기대상 100개입니다. 같은 간선을 두 번 세거나 새 간선을 생성해서 200개가 되는 것은 아닙니다. ‘기대상’은 해시를 새로 골라 실행하는 확률 실험의 평균에 대한 말이지 이번 실행의 모든 파일 크기가 똑같다는 뜻은 아닙니다.

**교육 포인트:** PTEBASE의 pairwise와 CTTP 원논문의 4-wise 가정을 동일하게 말하지 않는다. CTTP의 고확률 변형도 별도 분석이다.

**근거:** PTE §4.1, p. 4의 확률 가정 해설. 간선 900개·3색은 수식 대입 예시.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757) · [공개 출처 3](https://www.dei.unipd.it/~silvestri/assets/publications/PSKP14.pdf)

## 15. 색은 몇 개로 나눌까? RAM과 읽기 비용의 균형

**슬라이드 목적:** ρ를 정하는 기준을 메모리와 비용의 절충으로 설명한다.

**발표 대본:**
그래프가 클수록 부분 문제를 더 작게 나누고 싶습니다. 하지만 색을 무작정 늘리면 두 색, 세 색 조합으로 만들어지는 작업이 많아지고 같은 파일을 여러 작업이 반복해서 읽습니다. 논문은 PTEBASE의 세 색 작업이 읽는 기대 간선 수를 계산합니다. 서로 다른 두 색의 간선 묶음은 기대상 2m/ρ²이고 이 묶음을 세 개 읽으므로 합은 6m/ρ²입니다. 이를 한 작업의 가용 메모리 M 이하로 만들도록 ρ를 sqrt(6m/M)의 올림으로 고릅니다. 여기서 m은 간선 개수이므로 M도 간선을 몇 개 담을 수 있는지에 대응하는 메모리 단위로 맞춰야 합니다. 32GB라는 숫자를 간선 개수와 그대로 섞어 넣으면 안 됩니다. 실제 구현은 간선 표현뿐 아니라 인덱스와 작업 버퍼의 byte 비용도 따져야 합니다. 그리고 이 식은 기대 크기를 맞추는 기준입니다. 모든 실행의 RAM 수용을 보장하는 것은 아니며 작은 반례는 부록 C에 두었습니다.

**교육 포인트:** ρ 증가 → 작업 크기 감소, 그러나 작업 수와 반복 읽기 증가. M을 클러스터 전체 RAM으로 읽지 않는다.

**근거:** PTE §4.1, p. 4; §4.4, p. 7. ceil=올림, sqrt=제곱근. 기대값과 용량 보장의 구분은 해설.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 16. 한 작업 안에서 triangle을 찾는 방법

**슬라이드 목적:** Figure 3(a)의 이웃 집합 교차 예로 로컬 열거 연산을 이해시킨다.

**발표 대본:**  
논문의 Figure 3(a)를 단순화해 보겠습니다. 부분 문제 안에서 간선 `(u,v)`를 기준으로 u의 이웃 집합 `{v,a,b}`와 v의 이웃 집합 `{n,b}`를 교차합니다. 공통 원소는 b 하나이므로 `(u,v,b)`가 삼각형입니다. 이런 이웃 집합 교차가 열거의 기본 연산입니다. 그런데 type-3 문제라면 다른 두 간선은 각각 ik와 jk 파일에 있어야 합니다. 따라서 u와 v의 모든 이웃을 비교할 필요 없이, 올바른 색 방향에 속한 이웃끼리만 보면 됩니다. 이 관찰이 다음 버전인 PTECD의 출발점입니다.

**교육 포인트:** 화면에서 두 집합의 공통 원소 b를 직접 가리킨다. 그래프의 정점 순서는 논문처럼 degree 다음 ID로 정한 total order임을 기억시킨다.

**근거:** PTE §3.1, p. 3; Algorithm 2, p. 4; Figure 3(a), p. 5의 예시.

## 17. PTECD: 필요한 색의 이웃만 비교

**슬라이드 목적:** PTECD가 pivot 간선의 두 끝점에서 필요한 색의 이웃만 골라 교차한다는 원리를 앞 슬라이드의 예시에 이어 설명한다.

**발표 대본:**  
앞 슬라이드의 예시를 그대로 쓰겠습니다. 정점 색은 u가 0, v와 a가 1, n이 0, b가 2입니다. 기준이 되는 pivot 간선 (u,v)는 E_star[0,1]에 있습니다. 세 번째 정점의 색을 2로 정한 color-direction 호출에서는 u 쪽 이웃을 E_star[0,2]로, v 쪽 이웃을 E_star[1,2]로 제한합니다. BASE가 비교하던 이웃 집합 {v,a,b}와 {n,b}에서 관계없는 색의 정점을 교차 입력에서 제외하면, CD가 실제로 교차하는 집합은 {b}와 {b}입니다. 교집합 b는 그대로 남으므로 결과도 같은 삼각형 (u,v,b)입니다. 여기서 정점의 degree와 ID로 정한 순서는 간선과 삼각형의 중복 출력을 막기 위한 total order입니다. 그 순서로 놓인 끝점의 색 라벨이 E_star 파일의 키가 되며, 색 번호를 작은 것부터 다시 정렬하지 않습니다. 또한 이 한 호출만으로 모든 경우를 처리하는 것이 아니라, Algorithm 3의 여섯 color-direction 호출이 가능한 색과 방향 배치를 모두 나누어 담당합니다.

**교육 포인트:** 이 예에서는 결과를 바꾸지 않고 비교 집합만 줄었다. 정점 순서와 색 번호 순서를 혼동하지 않고, 여섯 호출이 전체 경우를 완전하게 나눈다는 점을 확인한다.

**근거:** PTE §4.2, Algorithm 3 및 Figures 3–4, pp. 5–6.

## 18. PTECD: Type-1 계산은 한 작업에만 배정

**슬라이드 목적:** PTECD가 Type-1 삼각형을 출력만 한 번 하는 데서 더 나아가, 계산 자체도 지정된 한 두 색 작업에서만 수행하도록 만드는 규칙을 설명한다.

**발표 대본:**  
색 수 rho가 4이고 모든 정점의 색이 0인 Type-1 삼각형을 생각하겠습니다. BASE에서는 색 0을 포함한 두 색 작업 (0,1), (0,2), (0,3)이 모두 색 0 내부 간선을 가지므로 같은 Type-1 후보를 세 번 계산할 수 있고, 중복 방지 조건에 따라 출력은 한 번만 합니다. PTECD는 색 c의 Type-1 계산 담당을 unordered pair (c, (c+1) mod rho)로 정합니다. 따라서 담당은 색 0이 01, 색 1이 12, 색 2가 23, 색 3이 03입니다. 색 0의 Type-1은 (0,1) 작업에서만 계산하고 한 번 출력하므로, 이 예에서는 세 번 계산하던 것을 한 번으로 줄입니다. 다만 다른 두 색 작업에서 색 내부 간선 파일을 전부 없애는 규칙은 아닙니다. 그 내부 간선은 Type-2 삼각형을 찾을 때 여전히 필요할 수 있습니다. 생략하는 것은 담당이 아닌 작업의 **Type-1 전용 열거 호출**뿐입니다.

**교육 포인트:** `한 번 출력`과 `한 번 계산`을 구분한다. 담당 규칙은 unordered pair이므로 색 3의 다음 색 0은 03 작업으로 표현한다.

**근거:** PTE §4.2, Algorithm 3 및 Figures 3–4, pp. 5–6.

## 19. PTESC: 파일 4개는 유지하고, 1개만 교체

**슬라이드 목적:** 계속 유지하는 공통 파일 4개와 교체하는 방향별 파일 1개를 구분해, 왜 사용이 끝난 파일을 해제할 수 있고 동시 적재가 5개면 되는지 설명한다.

**발표 대본:**  
PTESC의 SC는 scheduling입니다. 색 0,1,2를 다루는 한 세 색 작업에서, 계속 쓸 파일과 중간에 교체할 파일을 나누어 보겠습니다. 색 0과 1 사이에는 E_star[0,1]과 E_star[1,0], 색 1과 2 사이에는 E_star[1,2]와 E_star[2,1]이 있습니다. 이 네 파일은 두 단계의 계산에 걸쳐 계속 사용하므로 RAM에 유지합니다. 화면의 ‘공통 4개’가 이 파일들입니다.

남은 두 파일은 색 0과 2 사이의 E_star[0,2]와 E_star[2,0]입니다. 화면에서는 각각 0→2와 2→0 방향 파일이라고 부릅니다. Type-3 삼각형 하나에는 색 0 정점과 색 2 정점을 잇는 간선이 하나 있으므로, 그 간선은 두 파일 중 하나에만 속합니다. 따라서 찾을 삼각형을 0→2 파일이 필요한 경우와 2→0 파일이 필요한 경우로 나누어 처리할 수 있습니다. 화살표는 무방향 간선을 차수와 ID로 정한 정점 순서대로 기록했을 때의 색 방향입니다. 그래프를 방향 그래프로 바꾸거나 색 번호를 작은 것부터 정렬한다는 뜻은 아닙니다.

첫 줄에서는 공통 4개와 0→2 파일을 읽고, 0→2 파일이 필요한 삼각형을 모두 찾습니다. 이제 뒤에 남은 것은 반대 방향인 2→0 파일을 쓰는 계산뿐입니다. 따라서 둘째 줄에서 역할이 끝난 0→2 파일을 RAM에서 내려도 놓치는 삼각형이 없습니다. 이 순간에는 공통 4개만 남습니다. 셋째 줄에서 2→0 파일을 읽어 나머지 삼각형을 찾으면 다시 4+1, 즉 5개입니다. 두 반대 방향 파일을 동시에 유지할 필요가 없어 최대 동시 적재가 5개가 됩니다. 해제는 이 작업의 RAM에서 내린다는 뜻이고, 분산 저장소의 원본 파일은 그대로 남습니다.

논문의 Algorithm 4와 연결하면 앞 단계는 색 순서 (0,1,2), (0,2,1), (1,0,2)의 세 호출이고, 뒤 단계는 (1,2,0), (2,0,1), (2,1,0)의 세 호출입니다. 호출 (x,y,z)는 E_star[x,y]에서 기준 간선을, E_star[x,z]와 E_star[y,z]에서 이웃을 가져옵니다. 앞 세 호출만 E_star[0,2]를 사용하고, 뒤 세 호출만 E_star[2,0]을 사용합니다. 여섯 경우를 빠짐없이 처리하면서 각 파일을 이 한 부분 문제 안에서 한 번씩만 읽습니다. 다른 부분 문제에서도 그 파일이 필요할 수 있으므로 전체 실행에서 한 번만 읽는다는 뜻은 아닙니다. 이 동시 적재량 감소가 전체 읽기 감소로 이어지는 이유는 다음 장에서 설명합니다.

**교육 포인트:** 표를 위에서 아래로 짚으며 ‘공통 4개 + 0→2’, ‘0→2 사용 완료 후 해제’, ‘공통 4개 + 2→0’을 설명한다. 세부 순열은 질문이 나올 때 대본의 마지막 문단으로 보충한다. 한 부분 문제의 전체 파일 수 6개와 최대 동시 적재 5개를 구분한다.

**근거:** PTE §4.3, Algorithm 4 및 Figure 5, pp. 6–7.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 20. PTESC: 동시 적재 감소가 읽기 감소로 이어지는 이유

**슬라이드 목적:** 여섯 파일에서 다섯 파일로 줄어드는 동시 적재량이 색 수 rho의 선택을 거쳐 전체 반복 읽기를 줄이는 논리를 수식으로 연결한다.

**발표 대본:**  
rho가 같다면 PTESC가 각 작업에서 읽는 데이터 양 자체를 줄이는 것은 아닙니다. 차이는 동시에 필요한 기대 데이터 크기입니다. PTECD는 6m/rho², PTESC는 5m/rho²이므로 작업별 가용 RAM을 M이라 할 때 필요한 색 수를 각각 ceil(sqrt(6m/M))과 ceil(sqrt(5m/M))로 잡을 수 있습니다. 같은 M에서 PTESC가 더 작은 rho를 허용할 수 있다는 뜻입니다. 서로 다른 두 색 사이의 off-diagonal 파일 하나는 두 색 부분 문제 한 개와, 나머지 세 번째 색을 고르는 rho−2개의 세 색 부분 문제에서 읽힙니다. 합하면 총 rho−1개 작업입니다. 따라서 rho가 실제로 작아지면 그 파일의 반복 읽기 횟수도 줄고 전체 network read가 감소합니다. 다만 ceiling 때문에 두 식의 rho가 같을 수도 있으며, 이 크기는 무작위 색 배정에 대한 기대값이지 모든 실행의 메모리 상한 보장이 아닙니다. 이 효과는 여러 작업이 하나의 캐시를 공유해서 생기는 것이 아니고, 빅오를 바꾸는 개선도 아닙니다. §4.4가 설명하는 동일한 점근 복잡도 안의 상수 계수 개선입니다.

여기서 m과 M은 간선 수와 그에 대응하는 메모리 용량 단위로 맞춰 비교합니다. 실제 byte 예산에는 인덱스와 버퍼 비용도 필요합니다. 서로 다른 색 수에서는 파일 이름이 같아도 담기는 간선이 달라지므로, 설명의 핵심은 특정 파일 내용의 고정이 아니라 각 간선 파일이 참여하는 작업 수입니다.

**교육 포인트:** 인과관계는 `동시 기대 적재량 감소 → 같은 RAM에서 더 작은 rho 가능 → 파일이 참여하는 작업 수 rho−1 감소 → 반복 network read 감소`이다. rho가 실제로 같으면 이 경로의 절감도 생기지 않는다.

**근거:** PTE §4.3, Algorithm 4 및 Figure 5, pp. 6–7; §4.4, p. 7.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 21. TTP·CTTP와 PTE의 차이

**슬라이드 목적:** 차이를 한 장에서 데이터 흐름 중심으로 비교한다.

**발표 대본:**  
TTP는 색별 부분 문제를 만들 때 간선을 여러 번 shuffle합니다. CTTP는 이를 여러 round로 나눠 한 round의 공간 부담을 낮추지만 전체 복제와 반복 읽기는 남습니다. PTE는 간선을 먼저 한 파일에만 분할 저장하고, 이후 작업이 필요한 파일을 읽게 해 shuffle을 `O(|E|)`로 낮춥니다. PTECD는 정확히 필요한 색 방향만 비교하고, PTESC는 작업 내부 적재 순서를 바꿔 network read를 더 줄입니다. 즉 차별점은 더 많은 머신을 동원한 것이 아니라, **데이터를 언제 복제하고 언제 읽는가**를 재설계한 데 있습니다. 그 효과를 논문의 실험으로 확인하겠습니다.

**교육 포인트:** 복잡도 식보다 “복제 전송”과 “분할 후 선택 읽기”의 대비를 강조한다.

**근거:** PTE §2.4, §3.2, §4.1, §4.4; CTTP §4, §5.3. m은 입력 간선 수.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757) · [공개 출처 3](https://www.dei.unipd.it/~silvestri/assets/publications/PSKP14.pdf)

## 22. 논문의 실험 결과

**슬라이드 목적:** 성능, shuffle 감소, 처리 가능 규모를 실험 조건과 함께 정확히 전달한다.

**발표 대본:**  
실험은 master 1대와 worker 40대로 구성된 41대 클러스터에서 수행됐고, 각 머신은 32GB RAM을 가졌습니다. 가장 큰 ClueWeb12는 약 63억 정점, 720억 간선, 3조 개가 넘는 삼각형을 가집니다. PTE 계열은 이 전체 그래프를 처리했지만 비교 알고리즘들은 메모리, 정수 범위, 또는 제한 시간 문제로 더 작은 규모에서 멈췄습니다. 다만 이것은 2016년 논문이 사용한 구현과 환경에서의 비교입니다. 속도 수치도 조건을 붙여 봐야 합니다. PTESC의 최대 47배 성능 향상은 real-world 데이터 중 **SubDomain에서 CTTP와 비교한 결과**입니다. shuffle 최대 245배 감소는 전체 720억 간선 ClueWeb12가 아니라, ClueWeb12에서 뽑은 **약 360억 간선 규모의 실험 지점**입니다. 그리고 3조 개 삼각형을 모두 저장했다는 의미도 아닙니다. 열거할 때 로컬 콜백으로 전달했기 때문에 결과 전체를 70TB 파일로 물질화하지 않아도 됩니다. 마지막으로 이 결과가 말하는 범위와 한계를 정리하겠습니다.

**교육 포인트:** “최대” 수치 옆의 데이터셋과 입력 규모를 함께 가리켜 과장된 일반화를 막는다.

## 23. 정리와 적용 범위

**슬라이드 목적:** PTE의 핵심 기여 세 가지와 논문 해석의 범위를 남긴다.

**발표 대본:**  
정리하면 PTE는 세 병목을 순서대로 다룹니다. PTEBASE는 미리 분할해 shuffle을 줄이고, PTECD는 color-direction으로 불필요한 계산을 줄이며, PTESC는 부분 문제 내부 스케줄로 network read를 줄입니다. 핵심 교훈은 대규모 그래프 알고리즘의 성능이 연산식만이 아니라 중간 데이터의 생성, 저장, 이동 방식에 의해 결정된다는 것입니다. 색상 해시의 균형은 기댓값에 대한 분석이지 모든 그래프에서의 최악 경우 보장은 아니며, 논문은 2016년의 Hadoop·Spark 환경을 대상으로 합니다. 또한 이 논문만으로 PTE가 현재의 모든 플랫폼이나 Tenstorrent 장치에서 그대로 효율적이라고 결론 내릴 수는 없습니다. 그런 적용에는 메모리 계층, 통신 방식, 런타임에 대한 별도 검증이 필요합니다. 이상으로 발표를 마치겠습니다.

**교육 포인트:** 마지막 문장은 “연산보다 데이터 이동이 먼저 병목이 될 수 있다”로 다시 압축해도 좋다.


**근거:** PTE Definition 1, §4, §6. 현재의 모든 시스템에 대한 성능 보장은 아님.

## 24. 부록 A. 의사코드로 보는 전체 흐름

**슬라이드 목적:** 의사코드를 문법이 아니라 데이터 흐름으로 복습한다.

**발표 대본:**
이 의사코드는 PTECD와 PTESC의 흐름을 합쳐 설명한 교육용 요약이지 실행 코드가 아닙니다. 분할 단계에서 간선의 끝점 색을 순서대로 키에 담아 한 파일로 분류하고, 열거 단계는 작업에 필요한 파일을 직접 읽습니다. E_star 표기는 수식 명령이 그대로 표시되는 문제를 피하기 위한 읽기 쉬운 표기입니다. 원문의 ψ는 사용하지 않는 입력 키이며 정점이나 색이 아닙니다. 원문 Algorithm 1의 emit은 삼각형 출력이 아니라 간선을 색상쌍별로 모으기 위한 레코드 출력입니다. 세부 분기와 여섯 color-direction 경우는 원문 Algorithms 2–4를 확인해야 합니다.

**교육 포인트:** 설명용 표기를 바꾸어도 키의 순서와 분기 조건의 의미는 바꾸지 않는다.

**근거:** PTE Algorithms 1-4, pp. 4-6. 실행 코드가 아닌 PTECD/PTESC의 교육용 요약.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 25. 부록 B. 비용과 메모리 보장의 범위

**슬라이드 목적:** shuffle, network read, total work를 다른 측정량으로 읽는다.

**발표 대본:**
이 표의 세 행은 서로 다른 비용입니다. PTE의 선형 O(m)은 분할 단계의 shuffle 레코드 양에 대한 주장입니다. 이후 여러 작업이 파일을 반복해서 읽는 network read는 O(m^(3/2)/sqrt(M))로 남고, total work는 O(m^(3/2))입니다. 따라서 한 행의 개선을 전체 통신량이나 실행시간으로 확대하면 안 됩니다. 확률적 배정으로 계산한 평균 작업 크기와 매번 반드시 메모리에 들어간다는 확정적 주장을 구분하는 것도 같은 이유입니다.

**교육 포인트:** m은 입력 간선 수이고 M은 작업별 가용 메모리다. 위 식은 논문의 자원 모델 기준이다.

**근거:** PTE §2.4, §4.1, §4.4. 기대값과 실행별 용량 보장의 구분은 발표용 해설.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 26. 부록 C. 기대 크기가 작아도 실제로 넘칠 수 있다

**슬라이드 목적:** 기대값과 실제 최대 크기의 차이를 작은 숫자로 입증한다.

**발표 대본:**
중심 c가 네 잎 a,b,d,e와 연결된 별 모양 그래프입니다. 삼각형은 없고 간선은 네 개입니다. 중심 색이 0, a와 b가 1, d와 e가 2인 배정은 완전 독립적으로 색을 골라도 발생할 수 있습니다. M을 간선 세 개분이라고 놓으면 논문의 식은 ρ=3을 주고 세 색 작업의 기대 크기는 24/9, 즉 8/3이어서 M 이하입니다. 그런데 이 배정에서 (0,1,2) 작업은 E01의 두 간선과 E02의 두 간선을 실제로 읽어 네 개를 메모리에 올립니다. 평균은 세 개 이하인데 이번 실행은 네 개입니다. 이것은 실제 PTE 프로그램이 실패했다는 실험 보고가 아니라, 기대값 식만으로 매번 들어간다는 논증을 할 수 없다는 수학적 예시입니다. 높은 확률의 최대 부하를 말하려면 추가 분석이 필요합니다.

**교육 포인트:** 정답인 triangle이 없어도 입력 간선 적재는 필요하다. 평균과 상한을 구분한다.

**근거:** PTE §4.1의 기대 크기 식에 대한 교육용 반례. 논문 실험이나 실제 실패 보고가 아님.

[공개 출처 1](https://datalab.snu.ac.kr/~ukang/papers/pteKDD16.pdf) · [공개 출처 2](https://doi.org/10.1145/2939672.2939757)

## 부록: 예상 질문과 답변

### Q1. 논문의 external memory는 RAM인가요, 저장장치인가요?

아닙니다. 이 문맥의 external memory는 보통 RAM 바깥의 SSD나 HDD 같은 저장장치를 뜻합니다. I/O-efficient 알고리즘은 RAM에 다 못 넣는 그래프를 디스크로 처리하지만, 단일 머신의 저장 용량과 I/O 처리량은 여전히 한계입니다. 논문의 약 70TB는 ClueWeb12의 3조 개 삼각형을 정점 ID 세 개씩 단순 저장할 때 필요한 **출력 저장공간**의 대략값입니다. 입력 처리용 RAM과 출력 보관용 storage는 다른 병목입니다.  
근거: 원문 PDF pp.1–2, Sections 1, 2.1.

### Q2. Enumeration과 counting은 무엇이 다른가요? 3조 개 결과를 정말 저장했나요?

Counting은 삼각형의 총개수만 구하고, enumeration은 각 삼각형을 하나씩 발견합니다. 그러나 논문의 정의는 발견한 삼각형을 모두 유지하거나 외부로 내보낼 것을 요구하지 않습니다. 각 삼각형을 로컬 `enum(·)` 함수에 전달해 바로 세거나 분석할 수 있습니다. 따라서 논문이 3조 개의 삼각형을 열거했다는 말은 3조 개의 3-tuples를 파일로 저장했다는 뜻이 아닙니다.  
근거: 원문 PDF p.3, Definition 1 뒤의 설명.

### Q3. TTP가 GP를 constant factor만큼 개선한다는 것은 무슨 뜻인가요?

같은 색 수 `ρ ≥ 3`과 균등 무작위 정점 색 배정을 기준으로, GP의 전체 기대 shuffle 레코드 수는 `3m(ρ-1)(ρ-2)/(2ρ)`, TTP의 레코드 수는 정확히 `m(ρ-1)`입니다. 여기서 `m=|E|`입니다. GP는 같은 색 간선을 `(ρ-1)(ρ-2)/2`번, 다른 색 간선을 `ρ-2`번 전달합니다. TTP는 두 종류 모두 `ρ-1`번 전달합니다. 따라서 `ρ > 6`이면 TTP의 레코드 수가 GP의 기대값보다 작고, 큰 ρ에서 `TTP / E[GP]`는 `2/3`에 가까워집니다. 두 방법 모두 `Θ(mρ)`이므로 개선은 상수 계수에 해당합니다. 이는 같은 ρ에서의 레코드 수 비교이며, 같은 reducer 메모리에 맞춰 서로 다른 ρ를 쓰는 비교나 전체 실행시간에 같은 절감률을 적용할 수는 없습니다.  
근거: TTP 공개 원논문 §4.1-4.3, Lemma 2·Theorem 2; PTE §2.4·§3.2.

### Q4. Pairwise independence가 간선 분산을 고르게 보장하나요?

균등한 색상 범위와 pairwise independence를 가정하면, 한 간선의 두 끝점이 특정한 **순서 있는 색상쌍**에 배정될 확률은 `1/ρ²`입니다. 따라서 방향별 `E_star[i,j]`의 기대 간선 수는 `m/ρ²`입니다. 방향을 합친 서로 다른 두 색 사이 묶음은 `2m/ρ²`, 한 색 내부 묶음은 `m/ρ²`이므로 묶음 종류도 구분해야 합니다. 이 분석은 모든 실행에서 완벽히 고르다는 보장이나 고확률 최악 경우 보장이 아닙니다. 특히 하나의 허브 정점을 공유하는 많은 간선의 배정은 서로 상관될 수 있어 skew가 생길 수 있습니다.  
근거: 원문 PDF pp.3–5, Sections 3.2, 4.1의 coloring·memory-size 설정·방향별 묶음 정의. 기대값과 실행별 보장의 구분은 확률 가정에 대한 해설입니다.

### Q5. 왜 PTECD는 type-2와 type-3에서 여섯 방향을 검사하나요?

삼각형에는 pivot, port, starboard 세 간선이 있고, 서로 다른 색 또는 두 색이 정점 순서와 결합되면 가능한 color-direction 배치가 여섯 가지 생깁니다. PTECD는 각 배치에 맞는 세 간선 집합을 별도로 넣어 필요한 방향의 삼각형만 찾습니다. 여섯 호출은 같은 삼각형을 무조건 여섯 번 출력한다는 뜻이 아니라, 가능한 방향 경우를 빠짐없이 나누어 담당한다는 뜻입니다.  
근거: 원문 PDF pp.5–6, Algorithm 3, Figure 4.

### Q6. PTESC에서 6개가 5개로 줄었다는 것은 무엇인가요?

전체 간선 파일 종류가 6개에서 5개가 된다는 뜻이 아닙니다. 하나의 세 색 부분 문제에서 여섯 color-direction 호출을 수행할 때, 읽기와 해제 순서를 조정해 **동시에 메모리에 유지해야 하는 간선 집합의 최대 수**를 6에서 5로 낮춘다는 뜻입니다. 이 때문에 메모리 제약 아래 더 적은 색을 쓸 수 있고 network read가 줄어듭니다.  
근거: 원문 PDF pp.6–7, Section 4.3, Figure 5, Algorithm 4.

### Q7. 2016년 결과를 현재의 최고 성능으로 봐도 되나요?

안 됩니다. 논문은 당시의 Hadoop 1.2.1, Spark 1.5.1, GraphLab PowerGraph 2.2와 비교한 결과입니다. “최대 47배”와 “유일하게 ClueWeb12 전체를 처리”했다는 주장은 그 실험 환경과 비교 대상에 한정해야 합니다. 현재 state of the art를 판단하려면 이후 연구와 최신 시스템을 별도로 조사해야 합니다.  
근거: 원문 PDF pp.8–10, Sections 5.1.2, 5.2, 6.

### Q8. 이 논문으로 Tenstorrent에서 PTE가 잘 동작한다고 말할 수 있나요?

말할 수 없습니다. 이 논문은 CPU 클러스터의 Hadoop과 Spark 구현을 평가했으며 Tenstorrent 하드웨어를 다루지 않습니다. PTE의 데이터 분할 아이디어가 참고가 될 수는 있지만, 실제 적합성을 판단하려면 장치 메모리 용량, 호스트-장치 전송, 온칩 네트워크, 희소 그래프 연산 지원, 런타임의 분산 I/O 구조를 별도로 측정해야 합니다. 이는 논문 결과가 아니라 후속 연구 질문입니다.  
근거: 원문 PDF pp.8–10, Sections 5.1.2, 5.2.3, 6.
