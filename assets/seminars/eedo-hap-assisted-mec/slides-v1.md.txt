## 3. 왜 HAP 보조 MEC인가

원문의 출발점은 고정 지상 MEC가 coverage를 주기 어려운 원격 지역이다

- GD는 battery와 local CPU가 제한된 computing-intensive task를 받는다
- 멀리 있는 cloud로 모두 보내면 전송 지연·에너지·혼잡 문제가 커질 수 있다
- HAP은 넓은 영역을 덮는 airborne edge server로 모델링된다
- 하지만 한 HAP의 CPU와 radio capacity도 유한하다
- 따라서 여러 GD가 보내는 양과 HAP이 처리할 양을 함께 정해야 한다

핵심: HAP은 넓은 coverage를 주지만, 처리 용량이 제한된 공유 edge다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 1–2 Introduction

## 4. 작업의 경로와 두 queue

한 slot에서 GD backlog는 local CPU와 radio로 갈라지고, radio 경로만 HAP-side queue에 더해진다

- **레인 GD**
- **레인 무선**
- **레인 HAP**
  - **GD queue**: Q(t): 시작 backlog → A(t): 다음 갱신
  - **로컬 CPU**: f와 D_l 선택
  - **오프로딩**: D_o ≤ R tau
  - **로컬 처리**: D_l만큼 service
  - **HAP queue**: H: 기존 backlog → D_o: 새 유입
  - **HAP 할당**: C를 priority로 배정
- GD queue → 로컬 CPU (실선, 단방향)
- GD queue → 오프로딩 (실선, 단방향)
- 로컬 CPU → 로컬 처리 (실선, 단방향)
- 오프로딩 → HAP queue (실선, 단방향)
- HAP queue → HAP 할당 (실선, 단방향)

핵심: Q는 GD backlog, H는 HAP backlog다. 둘을 섞으면 제어 규칙을 잘못 읽는다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 3–4, Fig. 1 and Eqs. 5–8

## 5. 에너지 장부: 세 항을 함께 센다

P1의 E(t)는 GD local CPU, GD radio, HAP processing의 합이다


| 항 | 읽기 쉬운 식 | 커지는 이유 |
| --- | --- | --- |
| local | E_l = xi f² phi D_l | CPU 주파수와 local work |
| radio | E_o = D_o P / R | 전송량·전력, 낮은 rate |
| HAP | E_h = l_1 C | HAP이 처리한 bit |
| total | E = 각 GD의 세 항 합 | 세 경로를 함께 고려 |

핵심: 오프로딩은 local CPU 에너지를 줄일 수 있지만, radio와 HAP 에너지가 사라지는 것은 아니다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) p. 4, Eqs. 9–12

## 6. P1: 장기 평균 에너지, 네 feasibility 제약

목적은 long-run expected energy 최소화이며, latency 자체를 직접 최소화하는 식은 아니다


| 제약 | 의미 | 막는 오류 |
| --- | --- | --- |
| C1 | 0 ≤ f ≤ f_max | GD CPU 한계 초과 |
| C2 | 0 ≤ D_o ≤ R tau | 한 slot radio 용량 초과 |
| C3 | D_o ≤ Q | 없는 task 전송 |
| C4 | 0 ≤ C ≤ H | 없는 HAP task 처리 |

핵심: queue stability는 장기 Lyapunov 요구이고, C1–C4는 slot별 feasibility 제약이다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) p. 4, Eq. 13 and C1–C4

## 7. 긴 미래를 매 slot 제어로 바꾸기

EEDO는 queue 제곱합의 drift에 energy penalty를 더한 상한을 현재 slot에서 낮춘다

- 상태 Theta는 모든 Q와 H backlog를 모은 벡터다
- Lyapunov L은 Q²와 H²의 합으로 backlog 크기를 수량화한다
- drift는 다음 slot으로 갈 때 L이 얼마나 변하는지의 조건부 기대값이다
- drift-plus-penalty는 drift + V × expected energy다
- V가 커지면 에너지 항을 더 강하게 중시하는 설계가 된다
- Theorem 1의 upper bound를 최소화해 P2의 세 결정으로 분리한다

핵심: 미래 task를 예측하지 않고, 현재 backlog와 관측값으로 slot bound를 낮추는 제어다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 5–6, Eqs. 14–23 and Thm. 1

## 8. EEDO의 GD 결정은 두 갈래다

P2의 GD 부분은 local CPU와 radio offload를 따로 고른다. HAP allocation은 다음 슬라이드에서 다룬다

- **현재 상태**: Q, H, R, P, V
- **GD local**: f와 D_l 선택
- **GD radio**: D_o threshold
- **GD action**: local + offload
- **GD controls**: f, D_l, D_o

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 6–7, Eqs. 23–29 and Alg. 1

## 9. 결정 1: local CPU frequency

Eq. 25는 backlog가 크면 CPU를 올리려 하지만, CPU와 queue가 주는 상한으로 clip한다

- P2의 local 항은 V xi f³ tau - Q f tau / phi 다
- stationary candidate는 square-root of Q divided by 3Vxi phi 다
- 최종 f는 candidate를 f* 이하로 clip한다
- f*는 min of Q phi / tau and f_max 다
- local service는 D_l = f tau / phi 로 바뀐다
- Q가 큰 쪽은 service를 요구하고, V가 큰 쪽은 energy를 더 중시한다

핵심: local CPU rule은 backlog와 CPU 에너지의 균형이며, 장치 한계를 넘지 않는다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) p. 6, Eqs. 24–25

## 10. 결정 2: offload는 threshold rule

Eq. 27은 한 계수의 부호로 ‘rate 한계까지 보낼지, 0일지’를 정한다


| 계수 | 0 이하이면 | 0 초과이면 | 직관 |
| --- | --- | --- | --- |
| V P/R - Q + H | D_o = min(R tau, Q) | D_o = 0 | radio cost - GD urgency + HAP congestion |
| Q 증가 | offload 쪽으로 | 해당 없음 | GD backlog가 크면 보낼 유인이 큼 |
| H 증가 | 해당 없음 | local 쪽으로 | HAP backlog는 보내기를 억제 |
| P/R 증가 | 해당 없음 | local 쪽으로 | 비싸거나 느린 radio는 억제 |

핵심: offload-only가 아닌 이유는 H와 P/R가 같은 방향으로 무조건 전송을 막을 수 있기 때문이다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) p. 6, Eqs. 26–27

## 11. 결정 3: HAP의 남은 CPU를 배정하기

Algorithm 1은 유한 capacity C_h 안에서 H backlog가 긴 eligible GD부터 처리한다

1. **capacity**: C_h = f_h,max tau / phi_h
2. **priority**: V l_1 - H 오름차순 sort
3. **eligible**: 계수 0 이하인지 확인
4. **allocate**: C = min(H, C_h)
5. **repeat**: C_h를 줄이고 다음 GD

핵심: HAP은 무한 service 대신, 한 slot의 shared capacity를 priority 순으로 나눈다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 6–7, Eqs. 28–29 and Alg. 1

## 12. Algorithm 1의 한 slot 읽는 순서

결정 규칙과 queue update를 분리하면 ‘보낸 task가 언제 H에 더해지는지’를 혼동하지 않는다

1. **관측**: A, Q, H, R, P를 읽음
2. **GD CPU**: Eq. 25로 f와 D_l
3. **GD radio**: Eq. 27로 D_o
4. **HAP 배정**: C_h와 Eq. 29
5. **queue 갱신**: Q는 Eq. 7, H는 Eq. 8

핵심: Eq. 8은 H에서 C를 뺀 뒤 D_o를 더한다. 새 offload를 먼저 service하지 않는다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 4, 7; Eqs. 7–8 and Alg. 1

## 15. V trade-off: theorem이 실제로 말하는 것

Theorem 2는 arrival rate lambda plus epsilon과 Lemma 1의 조건 아래 energy와 average queue의 upper bound를 준다

- energy: E_EEDO ≤ E* + Z/V
- average queue: J-bar ≤ [Z + V(E-hat - E-check)] / epsilon
- 첫 bound는 V가 커질수록 Z/V 항이 작아진다
- 둘째 bound는 V를 포함하므로 backlog cost가 커질 수 있다
- epsilon, E-hat, E-check, Z와 Lemma 1의 존재 조건이 식에 들어간다
- 따라서 ‘V를 키우면 항상 더 좋다’는 결론은 theorem의 내용이 아니다

핵심: 핵심 trade-off는 energy gap의 1/V 항과 queue bound의 V 항을 함께 읽는 데 있다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) p. 7, Lemma 1 and Thm. 2; Eqs. 30–32

## 20. EEDO가 주장하는 것과 아닌 것

source claim의 범위를 보존하면 online optimization을 과장하지 않고 이해할 수 있다

- 주장: prior statistics 없이 current Q,H,R,P로 online decision
- 주장: model의 energy–queue bound 분석
- 주장: static-HAP simulation의 energy·queue 비교
- 비주장: reward를 학습하는 generic RL controller
- 비주장: 모든 실제 HAP network의 latency SLA 보장
- 비주장: HAP CPU·radio capacity가 무한함

핵심: current observation을 쓰는 online rule과 prior statistics 불필요는 양립한다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 1, 5–7, 11; Abstract, Eqs. 25–29

## 21. 마무리: 세 개의 제어와 한 개의 trade-off

EEDO는 partial offloading을 CPU·radio·HAP service 세 결정으로 나누고, V로 energy와 backlog를 조절한다

- 문제: remote-zone GD와 하나의 유한 HAP edge server
- 상태: GD queue Q와 HAP queue H를 분리해 추적
- 제어: local f, offload D_o, HAP service C
- 규칙: CPU square-root clip, radio threshold, HAP priority sort
- 근거: conditional Lyapunov bounds와 static simulation figures
- 한계: 모델·channel·parameter·static HAP 가정 밖은 별도 검증이 필요

핵심: 핵심 질문은 ‘얼마나 보낼까’보다, 어디에 backlog가 있고 어떤 energy를 감수할지다

근거: [paper](https://link.springer.com/article/10.1186/s13677-024-00645-5) pp. 4–11, Eqs. 5–32 and Conclusion
