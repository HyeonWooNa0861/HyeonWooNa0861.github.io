# CHESTNUT: 이동형 MEC QoS 데이터셋 읽기

논문: CHESTNUT: A QoS Dataset for Mobile Edge Environments

저자: Guobing Zou · Fei Zhao · Shengxiang Hu (2024)

## 1. CHESTNUT: 이동형 MEC QoS 데이터셋 읽기

Shanghai 위치·이동 trace를 바탕으로 MEC workload와 QoS를 생성한 arXiv v3 데이터셋 논문


근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 1; arXiv v3 metadata

## 2. 모바일 MEC QoS에는 시간과 위치가 함께 필요하다

같은 서비스라도 사용자 이동, 서버 coverage, 부하가 바뀌면 QoS 문맥이 달라진다.

1. **정적 matrix**: user·service QoS만 남기기 쉬움
2. **이동 사용자**: 위치와 요청 시각이 변함
3. **에지 서버**: coverage와 부하가 변함
4. **CHESTNUT**: 이 문맥을 한 dataset에 연결

핵심: 목표는 MEC QoS 예측용 문맥을 제공하는 것이지 특정 예측기의 승리를 보이는 것이 아니다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 1–2, abstract and introduction

## 3. 먼저 구분할 것: trace seed와 생성된 QoS

CHESTNUT은 두 Shanghai source dataset을 그대로 합친 raw telemetry table이 아니다.


| 구성 | 논문이 사용하는 입력 | CHESTNUT에서의 상태 |
| --- | --- | --- |
| 사용자 이동 | Taxi GPS 위치·속도·방향 | 정렬·선별한 user trace |
| 후보 서버 | Telecom base-station 좌표 | radius·supply를 부여한 server |
| 서비스·호출 | 원자료 없음 | demand·request를 합성 |
| load·rt·nj | 원자료 없음 | 생성 모델의 QoS 출력 |

핵심: 생성 요소를 실측 operator QoS로 부르면 데이터셋의 근거 범위를 넘는다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 2–7; Sec. I–III

## 4. 두 Shanghai source trace의 역할

source의 규모와 사용 범위를 함께 읽어야 proxy를 실제 MEC 측정으로 오해하지 않는다.


| source | 논문이 말한 범위 | CHESTNUT에서의 역할 |
| --- | --- | --- |
| Johnson Taxi | 특정 하루 GPS와 이동 상태 | mobile user trace seed |
| Shanghai Telecom | 7.2M records, 9,481 phones, 3,233 sites | base-station location seed |
| Telecom 사용 범위 | one month·Shanghai geography | candidate server simulation |
| 공개 release | paper가 Kaggle link를 명시 | dataset access path |

핵심: 택시와 기지국 좌표는 mobility·location proxy이며, 실측 MEC capacity trace가 아니다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 2, Sec. I and footnote, [kaggle-data](https://www.kaggle.com/datasets/sorriso07/chestnut) release link named on p. 2

## 5. CHESTNUT 구성 pipeline

trace의 provenance와 generator의 output을 한 흐름에 보되, payload를 분명히 적는다.

- **레인 dataset build**
  - **Shanghai traces**: GPS·site coordinates
  - **preparation**: align·filter·coverage
  - **MEC entities**: user·server·service
  - **generator**: invocation·load·rt,nj
- Shanghai traces → preparation: GPS·coordinates (실선, 단방향)
- preparation → MEC entities: aligned state (실선, 단방향)
- MEC entities → generator: context state (실선, 단방향)

핵심: 마지막 상자의 `rt,nj`는 trace에서 직접 읽은 열이 아니라 generator가 만든 QoS output이다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 2–7; Sec. II–III

## 6. 후보 edge server 만들기

기지국 좌표에 coverage와 상대 supply를 부여해 MEC server entity를 구성한다.

- **레인 server preparation**
  - **base-station 좌표**: 도시 경계 안 site
  - **coverage**: radius 400–3,200
  - **server entity**: location·radius·supply
- base-station 좌표 → coverage: site location (실선, 단방향)
- coverage → server entity: relative levels (실선, 단방향)

핵심: radius와 compute·storage·bandwidth level은 논문의 simulation configuration이다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 3, Fig. 1, Table I, Sec. II-A

## 7. 불규칙 GPS를 고정 시점 user trace로 정렬

이 time axis는 논문이 명시한 fixed-window snapshotting 절차를 보여 준다.

- **레인 user alignment**
  - **irregular GPS**: taxi record 시각
  - **Δt=30 window**: 마지막 record 유지
  - **aligned trace**: 없으면 일시 absent
- irregular GPS → Δt=30 window: GPS snapshot (실선, 단방향)
- Δt=30 window → aligned trace: system timestamp (실선, 단방향)
- 시간축: 왼쪽에서 오른쪽으로 진행

핵심: 최종 user trace는 raw taxi table이 아니라 alignment와 screening 뒤의 연구용 표본이다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 4, Fig. 2–4, Sec. II-C

## 8. 합성 서비스의 수요 수준

각 `sid`는 compute, storage, bandwidth의 세 상대 demand level을 갖는다.


| field | 값의 성격 | 논문 규칙 |
| --- | --- | --- |
| sid | synthetic service ID | 총 1,000 service |
| computing | relative demand | 1..Ps, Ps=4 |
| storage | relative demand | 1..Ps, Ps=4 |
| bandwidth | relative demand | 1..Ps, Ps=4 |
| 같은 tuple | 서로 다른 sid 가능 | latent app 차이를 모사 |

핵심: 같은 demand tuple도 다른 service ID가 될 수 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 3, Table I–II, Sec. II-B

## 9. QoS 예측의 단위: user–server–service–time

paper는 invocation을 R_i=⟨u,e,s,t⟩로 정의하고 sample rows에 QoS output을 붙인다.


| entity | key/state | 예시 field |
| --- | --- | --- |
| user | u at timestamp t | lon, lat, speed, direction |
| server | e covering u | location, radius, supply, load |
| service | s at t | compute, storage, bandwidth |
| invocation | (u,e,s,t) | uid, eid, sid, timestamp |
| generated QoS | invocation output | rt, nj |

핵심: random row split은 같은 user·server의 미래 state나 관계를 test에 섞을 수 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 5, 6, 8; Eqs. 10, Tables III, V–VI

## 10. 요청 시퀀스와 invocation 생성

공통 리듬과 개인 variation을 만들고, coverage 조건에서 server와 service를 연결한다.

1. **request group**: 공유 active timeline
2. **user signal**: GP trend + white noise
3. **coverage**: nearest covering server 선택
4. **invocation**: (u,e,s,t) record 생성

핵심: 같은 group도 user별 request trace는 다르다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 4–5; Sec. III-A, Eqs. 6–10

## 11. server load는 매 시점 독립 표본이 아니라 재귀 state다

이 time axis는 Section III-B의 prior load, current demand, release update를 압축한다.

- **레인 server load**
  - **prior state**: background load
  - **current demand**: supply와 mismatch
  - **next state**: recursive load·release
- prior state → current demand: remaining supply (실선, 단방향)
- current demand → next state: nonlinear update (실선, 단방향)
- 시간축: 왼쪽에서 오른쪽으로 진행

핵심: load history는 forecast에 유용하지만 random split 누수를 부른다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 5–6; Sec. III-B, Eqs. 11–17

## 12. response time·jitter 생성

둘 다 user–server–service–time 문맥을 쓰지만, paper의 생성 기제는 서로 다르다.

- **context**: u,e,s,t state
- **response time**: 6 delay stages
- **network jitter**: 5 mobility factors
- **perturbation**: edge·time factor
- **QoS output**: generated rt,nj

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 6–7; Sec. III-C–E, Eqs. 18–45

## 13. 가상 예시: coverage에서 QoS context key까지

아래 값은 CHESTNUT 원본 행이 아닌, schema를 손으로 읽기 위한 invented example이다.


| 항목 | 가상 값 | 해석 |
| --- | --- | --- |
| context key | uid=7, eid=2, sid=10, t=4 | 한 invocation 문맥 |
| coverage | distance 0.6 km, radius 1.0 km | 0.6 ≤ 1.0 이므로 cover |
| service demand | (compute, storage, bandwidth)=(3,2,4) | relative levels |
| forecast target | generated rt,nj | 과거 state만 input으로 사용 |

핵심: 가상 key는 원본 QoS event를 재현하지 않는다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 3, 5–8; Sec. II–III, Table VI

| entity | count | 읽는 방법 |

## 15. mobility와 coverage가 만드는 시간 의존성

Figures 6–7은 selected trace와 request-pattern generator의 성질을 보인다.


| 관찰 | paper의 수치/설명 | 평가상 의미 |
| --- | --- | --- |
| 평균 coverage 1 | 1,638 servers | 희소하지만 overlap 존재 |
| 평균 coverage 2 | 107 servers | coverage 관계를 feature로 사용 |

## 16. 생성 결과의 분포: QoS model accuracy와 구분

| 항목 | reported statistic | 해석 범위 |
| --- | --- | --- |
| service levels | 각 resource level 약 250 services | synthetic demand 균형 |

## 18. schema에서 만들 수 있는 조건부 연구 과제

paper가 언급한 MEC uses를 dataset의 실제 key와 context에 연결한다.

1. **QoS forecasting**: 과거 context로 rt,nj 예측
2. **service selection**: coverage 후보 안에서 선택
3. **load-aware simulation**: server state 변화 분석
4. **평가 설계**: time·entity split을 선언

핵심: CHESTNUT은 context-rich evaluation substrate로 쓸 수 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) p. 2; pp. 5–8, Sec. I–III

## 19. 평가 설계: row split 전에 막아야 할 누수

아래는 paper의 prescribed protocol이 아니라 schema를 읽어 도출한 evaluation safeguards다.


| 의존성 | naive split의 위험 | 명시할 분리 |
| --- | --- | --- |
| timestamp | 미래 load·요청 추세 노출 | chronological cutoff |
| same user | trajectory history 재등장 | user-held-out 또는 history rule |
| same server | coverage·load relation 재등장 | server/region generalization |
| request group | shared trend가 test에 섞임 | group information 공개 여부 확인 |

핵심: 무엇을 generalize하려는지 먼저 정해야 split도 해석할 수 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 4–8; Sec. II-C–IV-A

## 20. 사용 범위와 한계

dataset의 강점인 controllable MEC context가 동시에 generalization boundary를 만든다.


| 근거가 있는 주장 | 근거가 없는 확장 |
| --- | --- |
| Shanghai trace-seeded mobility/location context | 다른 도시·carrier·user population의 대표성 |
| model-generated response time와 jitter | operator telemetry와 동등한 실측 QoS |
| sampled radius·relative supply | 실제 MEC hardware/radio capacity |
| Table VII inventory와 Fig. 8–11 분포 | energy, security, packet-loss benchmark |
| feature comparison with WS-DREAM | predictor accuracy ranking |

핵심: 실제 network telemetry로의 validation을 별도 수행해야 deployment claim을 할 수 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 2–9; Sec. I–IV, Tables VII–VIII

## 21. CHESTNUT을 재현 가능하게 읽는 순서

source boundary, entity key, generator, evaluation scope를 순서대로 확인한다.

1. **provenance**: trace seed와 생성 output 분리
2. **schema**: u,e,s,t와 rt,nj 확인
3. **generator**: load·response·jitter 기제 확인
4. **evaluation**: split·city·telemetry 경계 명시

핵심: CHESTNUT의 가치는 dynamic MEC context와 생성 가정을 함께 보이는 데 있다.

근거: [arxiv-v3](https://arxiv.org/abs/2410.19248v3) pp. 2–9; Sec. I–IV
