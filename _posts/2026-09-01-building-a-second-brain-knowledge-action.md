Tiago Forte의 *Building a Second Brain*은 메모를 많이 모으는 방법보다, 정보를 실제 결과물로 전환하는 개인 지식 관리 시스템을 설명한다. 이 글은 한국어판의 들어가는 글과 1장부터 10장까지를 검토하고, CODE와 PARA를 중심으로 학습·연구·글쓰기 작업에 적용할 수 있도록 재구성한 해설이다.

> **핵심 메시지:** Second Brain의 목적은 정보 보관량을 늘리는 것이 아니라, 공명하는 자료를 수집하고 실행 단위로 정리한 뒤 핵심을 추출해 실제 결과물로 표현하는 데 있다. CODE는 이 흐름을 만들고 PARA는 현재 행동 가능성을 기준으로 자료의 위치를 정한다.

## 1. A Second Brain Is an Action System

정보가 부족해서가 아니라, 필요한 정보를 찾고 연결하고 다시 사용하는 과정이 불안정해서 일이 막히는 경우가 많다. Second Brain은 중요한 아이디어, 메모, 파일, 초안을 외부 디지털 시스템에 저장해 기억의 한계를 보완한다.

그러나 저장소 자체가 목표는 아니다. 좋은 시스템은 과거에 모은 지식을 현재 프로젝트에 다시 공급하고, 작은 메모를 문서·발표·연구·서비스 아이디어 같은 결과물로 발전시킨다. 기억, 연결, 창조가 하나의 흐름으로 이어질 때 메모는 아카이브를 넘어 생산 자산이 된다.

## 2. CODE: From Input to Output

CODE는 정보를 받아들이는 순간부터 표현하는 순간까지의 네 단계다.

| Stage | Guiding question | Practical behavior |
|---|---|---|
| Capture | 무엇이 나에게 공명하는가? | 모든 것을 저장하지 않고 놀라움, 유용성, 개인적 의미가 있는 조각을 남긴다. |
| Organize | 이 정보는 어디에서 행동에 쓰일 것인가? | 주제가 아니라 현재 프로젝트와 책임 영역을 기준으로 배치한다. |
| Distill | 미래의 나는 무엇을 가장 먼저 봐야 하는가? | 핵심 문장과 요점을 단계적으로 드러내 다시 읽는 비용을 줄인다. |
| Express | 이 재료로 무엇을 만들고 공유할 것인가? | 메모를 초안, 분석, 발표, 코드, 의사결정 같은 결과물로 조립한다. |

Capture에서 가장 흔한 실수는 가치 있어 보이는 모든 것을 모으는 것이다. 선택 기준은 객관적 완전성이 아니라 현재의 관심과 프로젝트에 대한 공명이다. 저장한 이유를 한 줄로 함께 남기면 나중에 맥락을 복구하기 쉽다.

## 3. PARA: Organize for Actionability

PARA는 정보를 주제가 아니라 실행 가능성에 따라 네 범주로 나눈다.

| Category | Meaning | Example |
|---|---|---|
| Projects | 완료 조건과 가까운 기한이 있는 결과 | 학회 발표 준비, 포트폴리오 배포 |
| Areas | 지속적으로 관리해야 하는 책임 | 연구 역량, 건강, 재무 |
| Resources | 앞으로 참고할 가능성이 있는 관심 주제 | LLM quantization, UI motion, writing |
| Archives | 완료되었거나 현재 비활성인 항목 | 종료된 프로젝트, 이전 학기 자료 |

폴더를 어디에 둘지 고민될 때는 “이 정보가 어떤 주제인가?”보다 “지금 어떤 결과를 움직이는 데 쓰이는가?”를 묻는다. 한 자료가 현재 논문에 직접 쓰인다면 Projects에 두고, 프로젝트가 끝난 뒤에도 장기적으로 관리할 지식이면 Areas나 Resources로 이동할 수 있다.

PARA의 장점은 완벽한 분류 체계를 만들지 않아도 된다는 점이다. 프로젝트가 바뀌면 정보도 이동하며, 사용 빈도가 낮아진 자료는 Archives로 보내 현재 화면의 밀도를 낮춘다.

## 4. Progressive Summarization

저장한 자료는 미래의 자신이 짧은 시간 안에 핵심을 되찾을 수 있어야 한다. Progressive Summarization은 모든 메모를 처음부터 완벽하게 요약하지 않고, 다시 사용할 때마다 중요한 부분을 한 단계씩 드러내는 방식이다.

1. 원문에서 필요한 발췌와 출처를 보존한다.
2. 다시 읽을 때 중요한 문장을 강조한다.
3. 그중 핵심만 더 강하게 표시한다.
4. 필요할 때 맨 위에 짧은 요약이나 실행 맥락을 쓴다.

이 접근은 정리 비용을 실제 사용 시점으로 미룬다. 한 번도 다시 보지 않을 자료에 과도한 시간을 쓰지 않고, 여러 번 재사용되는 메모만 자연스럽게 고밀도의 지식 단위로 발전한다. 출처 링크와 원문 맥락은 끝까지 남겨 요약이 근거와 분리되지 않게 해야 한다.

## 5. Intermediate Packets

큰 결과물을 처음부터 한 번에 만들려 하면 빈 화면에서 시작하는 부담이 커진다. Second Brain은 재사용 가능한 작은 작업 결과를 Intermediate Packets로 본다. 읽은 논문의 한 문단 요약, 실험 그래프, 코드 예제, 발표 도입부, 비교 표, 검증된 참고문헌 묶음이 모두 중간 패킷이 될 수 있다.

프로젝트를 진행할 때는 과거의 패킷을 검색해 조립하고, 부족한 부분만 새로 만든다. 이렇게 하면 이전 작업이 다음 작업의 출발점이 되고, 프로젝트가 끝나도 유용한 단위가 지식 자산으로 남는다.

중간 패킷은 완성본이 아니므로 출처, 상태, 사용 조건을 함께 표시하는 편이 좋다. 예를 들어 `draft`, `verified`, `needs-source` 같은 간단한 상태를 붙이면 오래된 초안을 확정된 사실처럼 재사용하는 일을 줄일 수 있다.

## 6. Creative Execution

책의 후반부는 메모 관리보다 창의적 실행에 집중한다. 자료를 넓게 모으는 발산 단계와, 하나의 결과를 향해 선택하고 결합하는 수렴 단계를 구분하면 두 작업이 서로 방해하지 않는다.

프로젝트 시작 시 관련 자료를 한곳에 모으고, 진행 중 생긴 중간 산출물을 계속 저장하며, 종료할 때 결과와 교훈을 정리한다. 체크리스트와 정기 리뷰는 기억에 의존하지 않고 이 순환을 반복하게 한다.

표현은 마지막 단계이면서 다음 Capture의 시작이기도 하다. 글이나 발표를 공개하면 피드백과 새로운 질문이 생기고, 그것이 다시 지식 시스템에 들어온다. 따라서 Second Brain은 개인 보관함보다 학습과 창작을 순환시키는 작업 환경에 가깝다.

## 7. A Practical Setup

처음부터 모든 파일과 메모를 이동할 필요는 없다. 현재 진행 중인 프로젝트 하나로 작은 시스템을 만드는 편이 빠르다.

1. 주로 사용할 메모 저장소 하나를 정한다.
2. `Projects`, `Areas`, `Resources`, `Archives` 네 범주를 만든다.
3. 현재 프로젝트 하나와 완료 조건을 적는다.
4. 그 프로젝트에 실제로 필요한 기존 메모와 파일만 옮긴다.
5. 새로 수집할 때 출처와 “왜 저장했는지”를 한 줄 남긴다.
6. 다시 사용한 메모에만 단계적 요약을 적용한다.
7. 이번 주에 만들 작은 결과물 하나를 정하고 메모를 조립한다.
8. 프로젝트 종료 후 재사용할 패킷을 남기고 나머지는 Archives로 이동한다.

특정 앱보다 입력 속도, 검색 가능성, 내보내기, 링크 보존, 백업 방식이 중요하다. 도구를 바꾸더라도 CODE와 PARA의 판단 기준은 유지할 수 있어야 한다.

## 8. Working with GTD

Second Brain과 GTD는 경쟁하는 체계가 아니라 서로 다른 층을 담당한다. GTD는 약속을 프로젝트와 다음 행동으로 명료화하고, Second Brain은 그 프로젝트에 필요한 지식 재료를 축적하고 변환한다.

예를 들어 “GTD 해설 글 게시”는 작업 시스템의 프로젝트가 될 수 있다. “공식 워크플로 지도”, “주간 검토 요약”, “인지과학 메모”, “표 초안”은 Second Brain에 보관되는 프로젝트 자료다. 작업 목록에는 다음 행동을, 지식 저장소에는 실행에 필요한 내용을 두면 두 시스템이 서로를 보완한다.

## 9. Design Risks and Extensions

Second Brain을 운영할 때 생기는 문제는 방법의 한계로 끝내기보다 해결 장치와 확장 경로를 함께 설계할 수 있다.

| Risk | Immediate solution | Scalable extension |
|---|---|---|
| 자료를 지나치게 수집한다. | 현재 프로젝트에 쓸 이유가 없는 항목은 저장하지 않는다. | 정기 리뷰에서 미사용 Resource를 Archives로 보내고 보존 기간을 정한다. |
| 분류 체계가 복잡해진다. | PARA 네 범주와 얕은 폴더부터 시작한다. | 프로젝트 이름과 상태 태그를 공통 규칙으로 사용해 도구가 늘어도 같은 구조를 유지한다. |
| 요약이 출처와 분리된다. | 원문 링크, 저자, 날짜를 메모에 함께 남긴다. | 검증 상태와 인용 메타데이터를 템플릿으로 만들어 연구·글쓰기 전체에 적용한다. |
| 메모는 많지만 결과물이 없다. | 매주 하나의 작은 Express 결과를 정한다. | 재사용 가능한 중간 패킷 라이브러리와 프로젝트 종료 리뷰를 운영한다. |
| 특정 앱에 종속된다. | 표준 형식 내보내기와 정기 백업을 확인한다. | Markdown·PDF·CSV처럼 이동 가능한 형식과 자동 백업 정책을 유지한다. |

## 10. 마지막 핵심 정리

Second Brain의 목적은 정보를 많이 보관하는 것이 아니라 **CODE로 지식을 결과물까지 이동시키고, PARA로 현재 행동 가능성에 맞게 배치하는 것**이다. 다시 사용할 메모부터 progressive summarization을 적용하고, 완벽한 자료를 기다리지 말고 intermediate packet을 조립해 작은 결과물을 만드는 흐름이 핵심이다.

- Capture에서는 현재 관심과 프로젝트에 공명하는 정보만 출처와 함께 남긴다.
- Organize에서는 주제보다 Projects, Areas, Resources, Archives의 실행 가능성을 기준으로 배치한다.
- Distill에서는 다시 읽는 비용을 줄이되 원문과 맥락을 잃지 않게 단계적으로 핵심을 드러낸다.
- Express에서는 축적한 메모를 문서, 연구, 발표, 코드와 같은 구체적 산출물로 전환한다.
